# Моніторинг wwwuabot

> Для власника проєкту. Технічне обґрунтування — `docs/CONSOLIDATION_PLAN.md` §5.8.

## Що вже працює

- **Workers Logs** увімкнено в усіх 4 воркерах: помилки й необроблені винятки видно в
  Cloudflare Dashboard → Workers & Pages → `<воркер>` → Logs. Безкоштовно:
  200 000 подій/добу, зберігання 3 дні.
- **`GET /health`** — воркер відповідає. Свідомо не торкається БД і KV: мусить бути
  миттєвим і не залежати від того, що перевіряє.
- **`GET /health/deep`** — живі D1 і KV; повертає **503**, якщо хоч одна недоступна.
  Саме цей ендпоїнт опитує зовнішній монітор.

## Крок 1. Задеплоїти зміну

Ендпоїнт `/health/deep` з'явиться в проді після пуша в `main` (CI деплоїть `api-dev`
автоматично). Перевірка у браузері:

```
https://api-dev.diskomate.workers.dev/health/deep
```

Має повернути `{"status":"ok","checks":{"db":true,"kv":true},...}`.

## Крок 2. UptimeRobot (безкоштовно, картка не потрібна)

1. Зареєструватись на [uptimerobot.com](https://uptimerobot.com).
2. **+ New monitor**.
3. **Monitor Type:** `HTTP(s)`.
4. **Friendly Name:** `wwwuabot api (prod)`.
5. **URL:** `https://api-dev.diskomate.workers.dev/health/deep`
6. **Monitoring Interval:** `5 minutes` (швидше — лише на платному плані).
7. **Alert Contacts:** свій email, галочка «To be alerted».
8. **Create monitor**.

Безкоштовний план: **50 моніторів**, перевірка раз на 5 хвилин.

### Чому саме `/health/deep`

`/health` не торкається бази — він скаже «все добре», навіть коли D1 лежить, тобто
дасть фальшиве заспокоєння. `/health/deep` віддає 503, і монітор це побачить.

### Що робити, коли прийшов лист «Down»

1. Відкрити `https://api-dev.diskomate.workers.dev/health/deep` — у відповіді буде
   `checks`. Те, що дорівнює `false`, і є зламана залежність (`db` або `kv`).
2. Cloudflare Dashboard → Workers & Pages → `api-dev` → **Logs**: там буде рядок
   `[api] /health/deep degraded`.
3. [Cloudflare Status](https://www.cloudflarestatus.com) — можливо, це збій на боці
   Cloudflare, і робити нічого не потрібно.

Текст помилки назовні не віддається (ендпоїнт публічний, а повідомлення D1 бувають
детальними), тому деталі шукай саме в логах.

## Крок 3. Sentry — стек-трейси помилок

UptimeRobot каже **що** впало, Sentry — **чому**. Безкоштовний план: 5 000 помилок/місяць,
30 днів зберігання, картка не потрібна.

### Що вже в коді

| Воркер | Що зроблено |
|---|---|
| `api-dev` | `Sentry.withSentry` ловить необроблені винятки з будь-якого контролера; з'явився явний обробник 500 — клієнт отримує `{"error":"Internal error"}`, а стек іде в Workers Logs і Sentry |
| `bot-dev` | `withSentry` на `fetch` **і** на споживачі черги; помилки, які grammY перехоплює сам, звітує `bot.catch` |

Важливе про дані: перформанс вимкнено (`tracesSampleRate: 0`), `dataCollection` вимкнено,
а `beforeSend` додатково вирізає заголовки, cookie, тіло й query-параметри. Це не
формальність — у заголовку їде Telegram `initData` (ним можна видати себе за користувача,
поки підпис не сплив), а в cookie — `admin_session`.

Без секрету `SENTRY_DSN` SDK не робить нічого: деплой без нього безпечний, а вмикається
Sentry одним секретом, без зміни коду.

### Крок 3.1. Створити проєкт

1. [sentry.io](https://sentry.io) → реєстрація, **картка не потрібна**.
2. **Create project** → platform: `Cloudflare Workers` → назва: `wwwuabot-api`
   (організація — `diskant`, регіон приймання — EU, `ingest.de.sentry.io`).
3. Лишити тільки **Error Monitoring**; Logging, Tracing і Application Metrics — вимкнені.
4. Скопіювати **DSN** — рядок виду `https://<key>@o<org>.ingest.de.sentry.io/<project>`.

> Банер «TRIAL IS ACTIVE · 14 days» — це маркетинговий тріал Business, увімкнений за
> замовчуванням. Картки немає, тож через 14 днів організація сама падає на безкоштовний
> **Developer** (5 000 помилок/міс, 30 днів, 1 користувач). Наш код і так працює рівно
> в межах безкоштовного: перформанс, логи й аналітика вимкнені явно.

### Крок 3.2. Додати DSN як секрет Cloudflare (не в репозиторій)

Cloudflare Dashboard → Workers & Pages → **`api-dev`** → Settings → Variables and Secrets →
**Add** → Type: **Secret** → Name: `SENTRY_DSN` → Value: DSN → **Save**.
Те саме для **`bot-dev`** (можна той самий DSN — тоді обидва воркери будуть в одному проєкті).

Секрет застосовується одразу, нового деплою не потрібно.

> **Стан на 12.09.2026:** секрет `SENTRY_DSN` додано в **обох** воркерах, код задеплоєно
> (CI run `34662385702`). Критий шлях перевірки — уже після реальної помилки в проді;
> див. «Якщо подій немає» нижче.

### Крок 3.3. Перевірити

Sentry → **Issues**: подія з'явиться після першої реальної помилки. Якщо порожньо кілька
днів — це нормально: означає, що в проді нічого не падає.

Якщо хочеться переконатись, що **DSN живий**, не чекаючи помилки — можна надіслати одну
подію прямо в приймальний ендпоїнт. Ключ і id проєкту беруться з DSN
(`https://<key>@<host>/<project_id>`), тому секрет у команду не вписується:

```bash
curl -sS -X POST -H "Content-Type: application/json" \
  -H "X-Sentry-Auth: Sentry sentry_version=7, sentry_key=$KEY, sentry_client=check/1.0" \
  -d '{"event_id":"0f1e2d3c4b5a69788796a5b4c3d2e1f0","message":"DSN check","level":"info"}' \
  "https://$HOST/api/$PROJECT/store/"
```

`HTTP 200` і `{"id":"..."}` означають, що проєкт приймає події. Це саме те, як
перевіряв агент 11.09.2026 — подія «wwwuabot: перевірка DSN» у Issues саме звідти, її
можна видалити.

**Важливо:** ця перевірка доводить тільки те, що DSN і проєкт робочі. Що події надсилає
сам воркер — видно або з реальної помилки, або з Workers Logs.

### Якщо подій немає

Це може бути нормою: без помилок подій і не буде. Але є один справді тихий ризик —
**ім'я секрету**. Якщо замість `SENTRY_DSN` стоїть, скажімо, `SENTRY_DNS`, воркер його
не побачить і Sentry лишиться вимкненим **без жодної помилки**. Тому при найменшому
сумніві варто перевірити саме ім'я (у дашборді воно обрізане — натисни олівець).

Друга ознака — **Workers Logs** (Workers & Pages → воркер → Observability → Logs): якщо
SDK не зміг стартувати, він скаржиться саме туди, з префіксом `[Sentry]`.

### Чому не для `web-platform-dev` і `web-admin-dev`

Там помилки живуть у браузері, і DSN треба вшивати в бандл на етапі збірки — це окремий
механізм (секрет GitHub Actions + `VITE_`-змінна). Додамо, коли з'явиться трафік: зараз це
дало б більше шуму, ніж користі.
