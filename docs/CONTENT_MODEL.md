# Контент сторінок: одна таблиця, два подання

**Створено:** 13.09.2026 · **джерело правди про код:** `packages/shared/src/content/`
і `packages/shared/src/database/tables.ts` · **схема таблиць:** [`DATA_MODEL.md`](./DATA_MODEL.md)
· **історія кроку:** [`log/journal-2026-09-13-pages-table.md`](./log/journal-2026-09-13-pages-table.md)

> **Рішення власника (13.09.2026).** «Щось лишається одне: 4 таблиці → 1.» Рядок — це
> сторінка вебу **разом із її поданням у боті**. Бот показує або повідомлення з кнопками
> (`callback` чи `web_app` — перехід на **ту саму** сторінку), або те саме повідомлення з
> посиланням на платформу.

## 1. Що було (і чому це справді була каша)

| Сховище | Хто писав | Хто читав |
|---|---|---|
| `scenarios` | адмінка, вкладка «Портал» | **бот** + платформа |
| `scenarios-admin` | адмінка, вкладка «Адмін» | **ніхто** поза адмінкою |
| `sites` + `site_pages` | платформа `/api/sites/*` | платформа `/view/:slug` |

Один тип контенту — `PageConfig` у колонці `page_data` — лежав у **чотирьох** таблицях. Правило
«яка сторінка відповідає цьому URL» було написано **чотири** рази й по-різному: SQL в API,
`splat || "__base__"` у платформі, `pages.find(…) ?? pages[0]` у `SiteRenderer`, `getScenario`
в боті. Навігація сайту при цьому жила ще й **п'ятим** списком — `sites.settings.navigation`
дублював назви сторінок, які вже існували рядками в `site_pages`.

Три дефекти, які це породжувало: контент вкладки «Адмін» не показувався **нікому**;
`title`/`photo_url` не вибирались із бази (у блоках завжди `null`); вимкнений сценарій зникав
із вебу, але працював у боті.

## 2. Цільова модель

> **Сторінка — одиниця контенту. Група сторінок — це та сама таблиця з `kind = 'collection'`.
> Бот і веб — два подання одного рядка.**

| Колонка `pages` | Що це | Було |
|---|---|---|
| `id` | стабільний ключ рядка | `sites.id`, `site_pages.id`; у сценаріїв ключем був `codeword` |
| `slug` | адреса вебу (`''` — головна) | `web_slug`, `site_pages.slug`, `sites.slug` |
| `codeword` | ключ діплінка бота | `scenarios.codeword` |
| `title`, `photo_url` | метадані сторінки | `title`, `photo_url` / `thumbnail` |
| `blocks` | контент для `PageRenderer` | `page_data` |
| `bot` | подання для Telegram: підписи, кнопки, богате повідомлення | `caption_*`, `buttons`, `rich_message`, `rich_data`, `price`, … |
| `kind` | `page` або `collection` | `sites` як окрема таблиця |
| `parent_id`, `position` | група та порядок; **навігація більше не зберігається** | `site_id`, `order_index`, `settings.navigation` |
| `owner_id` | власник групи | `sites.owner_id` |
| `status`, `visibility` | один автомат: `draft · pending · published · rejected` + `private · public` | `is_active`, `sites.status`, `site_pages.status`, `is_public` |
| `meta` | залишок без власної колонки (`template_id`, SEO, службові позначки) | `site_pages.meta`, `settings` |

Чотири речі, які з цього випливають:

1. **Адреса унікальна** в межах групи й типу (`idx_content_slug`) — раніше за це відповідали
   три різні механізми, з яких у `scenarios` не було жодного.
2. **`codeword` унікальний** (`idx_content_codeword`, частковий індекс) — саме тому діплінк
   `t.me/<bot>?start=<codeword>` однозначно вказує на сторінку.
3. **Навігація обчислюється**, а не зберігається: дочірні рядки групи за `position`.
4. **`bot` — подання, а не друга правда.** Цільовий стан — коли він виводиться з `blocks`;
   поки що це окрема колонка, щоб перенос нічого не втратив (фаза 5).

## 3. Бот як шар сторінки (те, що дає `codeword`)

| Крок | Хто | Механізм |
|---|---|---|
| 1. Користувач тисне «Поділитись» → «Копіювати посилання» | сторінка | `https://t.me/<bot>?start=<codeword>` |
| 2. Перехід за діплінком | бот | `/start <codeword>` (вже працює — `bot-dev/src/core/router/bot-router.ts`) |
| 3. Бот відповідає | бот | повідомлення рядка: підпис + кнопки; серед них — `web_app` на сторінку |
| 4. Користувач відкриває сторінку | платформа | `/view/<slug>` або `/<slug>` — той самий рядок |

Кнопка «Поділитись» — **нове**, і вона можлива саме тому, що `codeword` тепер унікальний у
всій таблиці, а не «десь у сценаріях». Базову адресу платформи беремо з конфігурації, не з коду.

## 5. Запуск міграції

```bash
npm run migrate:content -- --dry-run     # показати зібраний SQL, нічого не виконувати
npm run migrate:content                  # локальна база (wrangler --local)
npm run migrate:content -- --remote      # дев-база (потрібен CLOUDFLARE_API_TOKEN)
```

Скрипт збирає схему **з реєстру** (не має власного DDL), застосовує перенос і друкує звіт:
скільки рядків доїхало з кожної таблиці, які адреси в легасі-даних займали кілька рядків і що
саме пропущено. Пропущене лишається в легасі-таблиці — рішення ухвалює власник.

## 6. Відомі обмеження

- **Читачі ще на старих таблицях** (фаза 3). Твердження «контент тепер в одній таблиці» було б
  неправдою без цього застереження: `pages` заповнена, але поки що ніким не читається.
- **Дві головні сторінки** — `__base__` (веб) і `main` (бот). Міграція переносить їх як два
  рядки; злиття — правка читача у фазі 3.
- **`rich_data`** (Telegram-розмітка) лишається в `bot` як є: це не `PageConfig`, і доки немає
  мапера (фаза 5), він є окремим джерелом для одного повідомлення.
- **Доступу до D1 у середовищі немає** — міграцію на деві запускає власник (або дає токен).
