## 0. Як саме мірялося (щоб цифру можна було перевірити)

| Що | Як |
|---|---|
| Мертвий код | обхід графа імпортів від точок входу (`main.tsx`, `worker.ts`, `router.tsx`, `exports` у `package.json` пакетів), включно з динамічними `import()` |
| Спільний код ↔ CSS | множина класів, які рендерить `packages/ui`, проти множини селекторів усіх `.css` |
| Мертвий CSS | клас, якого немає в `src/` **навіть як підрядок** (це **нижня** оцінка: динамічно склеєні імена невидимі статично) |
| Покриття тестами | не coverage-інструмент, а граф: скільки модулів `src/` імпортується з тестів |
| Вага бандла | `ls -la` по `dist/` після `vite build` обох оболонок |
| Уразливості | `npm audit` |

**Чого цей аудит НЕ містить:** вимірювання продуктивності в рантаймі, візуальної
перевірки, E2E-тестів, пентесту, аналізу користувацьких сценаріїв на пристроях.
Нічого з цього в середовищі аудиту зробити неможливо — і це прямо знижує впевненість
у критеріях 6 (мобільність) і 9 (продуктивність).

**Зміна, яку аудит уже спричинив:** знайдено й видалено **74 недосяжні файли
(5 238 рядків, 15% коду)** — деталі в §4.1 і в `CONSOLIDATION_LOG.md` §9. Усі цифри
нижче — **після** цього видалення.

## 1. Критерії: за якою системою оцінюється

Власної «системи» не вигадувалось. Рубрика зібрана з визнаних моделей, адаптованих
під цей проєкт (Cloudflare Workers + React + D1, мобільний TMA пріоритет №1):

| Джерело | Що взято |
|---|---|
| **ISO/IEC 25010 (SQuaRE)** | характеристики: maintainability, security, reliability, performance efficiency, usability/accessibility, compatibility |
| **CISQ / OMG** measures for maintainability | мертвий код, дублювання, розмір модулів, складність |
| **SIG/TÜViT** maintainability model | розмір файлів (200/400 рядків) як поріг читабельності |
| **WCAG 2.2 AA** | доступність: семантика, фокус, розмір тап-таргетів |
| **`AGENTS.md` §3, §7** | локальні норми проєкту (кристалевість, заборона `SELECT *` на `users`, нативних діалогів, класу без CSS) |
| **DORA / CI-зрілість** | гейти, що блокують деплой; відтворюваність збірки |
| **Bundle budget** | вага чанка як окремий критерій для TWA |

Кожен критерій має вагу і 2–7 перевірок. Перевірка дає **2** (норма виконана),
**1** (частково) або **0** (ні). Оцінка критерію = набрані бали ÷ максимальні × 10.
Підсумок = сума (оцінка × вага) ÷ 100.

**Вага навмисно не рівна.** Мобільна доступність (15) і тести (15) важать більше за
косметику: це єдиний продукт, який бачать користувачі, і єдине, що ловить регресії.

## 3. Де ми на шкалі зрілості

| Рівень | Стан |
|---|---|
| **L2 — керований** (правила діють для частини коду) | ✅ є |
| **L3 — визначений** (правила писані, гейти блокують деплой) | ✅ є — і це головний актив: CI, Prettier, lint, тести, `wrangler-env.test.ts` |
| **L4 — вимірюваний** (числові пороги в CI) | ❌ **немає жодного**: ні порогу покриття, ні бюджету бандла, ні перевірки ліміту рядків, ні перевірки «клас без CSS» |
| **L5 — оптимізуючий** | ❌ |

**Головний висновок:** проєкт виглядає як L3, але **ніщо не заважає йому котитися
назад у L2**, бо якість ніде не вимірюється автоматично. Саме тому 44 класи без CSS
і 15% мертвого коду прожили місяці: гейти перевіряють, що код *компілюється*, а не
що він *потрібен*.

## 7. Межі цієї оцінки (читати перед цитуванням)

1. **Немає рантайм-вимірювань.** Продуктивність оцінена за вагою зібраних файлів, не
   за профілем у браузері чи на телефоні.
2. **Немає візуальної перевірки.** Прев'ю воркерів у середовищі аудиту немає, тому
   всі висновки про верстку — з CSS і розмітки, а не з екрана.
3. **Мертвий CSS — нижня оцінка.** Іменa, склеєні рядками (`wb-${x}`), статично
   невидимі; справжня цифра може бути більшою.
4. **Ваги — рішення, не істина.** 15 для мобільності обрано свідомо (TWA = телефони).
   Зміниш ваги — зміниться відсоток, і це нормально для будь-якої рубрики.
5. **Прода немає.** Тому «надійність» тут вимірюється тестами й гейтами, а не
   поведінкою під навантаженням.
