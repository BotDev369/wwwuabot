# 13.09.2026 — Схема D1: реєстр таблиць і гейт `check:db`

**Коміт:** див. §0 плану · **карта таблиць:** [`docs/DATA_MODEL.md`](../DATA_MODEL.md)

Причина появи цього запису — скарга власника «каша з сценаріями і таблицями, кожен AI своє
нагородив» із знімком списку таблиць у дашборді Cloudflare: `mydate_analysis`, `scenarios`,
`scenarios-admin`, `settings`, `site_pages`, `sites`, `templates`, `users`. Розбирав не на
здогадах: зібрав усі SQL-звернення до таблиць по воркспейсах і знайшов, **хто з них
створюється, а хто — ні**.

## 1. Що знайшлось (виміряно, не оцінено)

| Факт | Як перевірено |
|---|---|
| `users` не створює **ніхто** | `grep -rn "CREATE TABLE users"` — 0 збігів; `withAutoMigrate` уміє лише `ALTER` наявної таблиці |
| `mydate_analysis` не створює **ніхто** | те саме: тільки `SELECT` і `INSERT` у `api-dev/src/shared/mydate-helpers.ts` |
| `scenarios` створювалась без `IF NOT EXISTS` | `api-dev/src/controllers/scenarios.controller.ts` — перевірка `sqlite_master`, потім голий `CREATE TABLE scenarios` |
| дві схеми сценаріїв розійшлися | `scenarios` — 23 колонки, `scenarios-admin` — 13; решта додавалась `ALTER`-ом із помилки SQLite |
| `web_config` ніхто не вживає | оголошена в старому DDL, 0 звернень у `src/` |

Найгірше тут не дублювання, а **два дефекти, яких не видно на робочій базі**: `users` і
`mydate_analysis` існували лише тому, що їх колись створили руками в дашборді. На чистій базі
перший же новий користувач і `/api/mydate/analysis/*` падали б з `no such table` — тобто
дефект чекав на першу ж спробу розгорнути базу заново.

## 2. Що зроблено

**Реєстр — єдина точка правди:** `packages/shared/src/database/tables.ts`. Оголошені всі вісім
таблиць: ім'я, власник, призначення, `CREATE TABLE IF NOT EXISTS`, індекси.

Дві свідомі деталі конструкції:

- **колонки виводяться з DDL, а не з окремого списку.** Два списки («DDL» і «колонки»)
  розходяться — рівно так `scenarios-admin` отримав схему, якої ніхто не оголошував;
- **`ensureTables` тільки додає**: `CREATE TABLE IF NOT EXISTS` і `ALTER … ADD COLUMN` для
  відсутніх колонок (список відсутніх дає `PRAGMA table_info`, а не серія помилок). Нічого не
  видаляє, не перейменовує, не змінює типів — тому безпечний на живій базі з даними.

**Прибрано механізм «схема з помилки».** `scenarios.controller.factory.ts` ловив
`no such column` і сам додавав колонку — саме так таблиця адмінки тихо доростала тим, що
надіслав інтерфейс. Тепер цих гілок немає: колонка або оголошена, або її не буде.

**Переведено на реєстр:** `services/sites/schema.ts` (стала 25 рядків замість 114),
`scenarios.controller.ts`, фабрика сценаріїв, `settings.repository.ts`, `user.repository.ts`
(гарантія на шляху `createUser` — там `INSERT`, який не обгорнутий `withAutoMigrate`),
`mydate-helpers.ts`.

## 3. Гейт `check:db`: чому саме такий

Без гейта каша повернеться: ні компілятор, ні тести не бачать ні імені таблиці, ні `CREATE
TABLE`. Перевіряються чотири речі: `CREATE TABLE` тільки в реєстрі; кожне ім'я в SQL
(`FROM`/`INTO`/`UPDATE`/`JOIN`) оголошене; `ALTER TABLE` — тільки для оголошених; `ensureTables`
не кличе неіснуючу таблицю.

**Ключові слова шукаються у верхньому регістрі — і це не смак.** Перша версія шукала без
урахування регістру й дала 100+ хибних спрацювань: `import … from "react"` ставало «таблицею
react», `log("update received")` — «таблицею received». Список виключень довелося б
поповнювати після кожного нового рядка логу — а такий гейт або вимкнули б, або він перетворився
б на ритуал. SQL у проєкті й так пишеться великими літерами, тож правило «SQL — верхній
регістр» стало частиною перевірки (і записане в `AGENTS.md` §7).

Гейт перевірено **негативно** — файлом-приманкою з `CREATE TABLE ghosts`, `FROM phantoms` і
`ALTER TABLE poltergeist`: усі три порушення він назвав із файлом і рядком. Гейт, який не
падає на порушенні, — це не гейт.

## 4. Чого НЕ робили — свідомо

- **Не об'єднали `scenarios` + `scenarios-admin`.** Це відкрите рішення власника (план §4 п. 1).
  Об'єднання чіпає живі дані й міняє поведінку бота: без фільтра `scope` у читанні адмін-сценарій
  із тим самим `codeword` заступив би портальний. Порядок кроків записаний у `DATA_MODEL.md`,
  щоб рішення не починалось із нуля.
- **Не перейменували `scenarios-admin`** у `scenarios_admin` (дефіс вибивається зі стилю
  `site_pages` / `mydate_analysis`): `ALTER TABLE … RENAME` — це міграція на живій базі, і їй
  місце поруч з об'єднанням, а не окремим комітом «заодно».
- **Не чіпали `INSERT INTO users (… ) VALUES (?, '...', …)`** у `my-dates.controller.ts`:
  api-dev створює рядок користувача з фальшивими іменами. Це справжня вада (таблиця `users`
  належить `bot-dev`), але без знання `NOT NULL`-обмежень живої таблиці будь-яка правка тут —
  вгадування. Записано в план як окремий пункт.

## Перевірка

- `npm test` — **264** тести (було 250): 14 нових на реєстр (інваріанти, розбір колонок із DDL,
  «тільки додає», пам'ять на `db`);
- `npm run typecheck` — 6 воркспейсів чисто;
- `npm run check:db` — 8 таблиць, поза реєстром не створюється жодна; негативна перевірка
  приманкою — падає, як мусить;
- `check:css` · `check:quality` · `check:docs` · `lint` · Prettier — зелені.

**Побічний ефект, який варто знати:** двійник D1 у тестах (`services/sites/fake-db.ts`) тепер
класифікує `PRAGMA table_info` як **схему**, а не як читання даних. Інакше прагма зсувала
індекси в `fake.reads`, і тести, що перевіряють «сторінки навіть не запитувались», падали б із
неправильної причини. Це не послаблення тестів: прагма справді стосується схеми.
