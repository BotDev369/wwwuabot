## 0. Що тут означає «консолідація»

Це **не** злиття двох воркерів в один. Рішення про роздільні воркери вже затверджене в
[PAGE_ENGINE_ARCHITECTURE.md](../PAGE_ENGINE_ARCHITECTURE.md) (09.09.2026) і має обґрунтування,
яке я перевірив і вважаю слушним:

1. **Zero bundle leakage** — адмінський JS фізично не потрапляє в бандл користувача.
   _Перевірено: це правда вже сьогодні, бандли окремі._
2. **Same-Origin Policy** — адмінська cookie не читається з публічного домену.
   _Перевірено: хости різні (обидва на `*.workers.dev`; власних доменів немає)._
3. **Cloudflare Access** — edge-захист адмінки не існує, якщо об'єднати.
   _Уточнено 12.09.2026: Access на адмінці **поки не налаштований** — це аргумент на
   користь роздільних воркерів, а не опис поточного захисту. Єдиний барʼєр зараз —
   cookie `admin_session` + адмін-гейт в `api-dev`._
4. **Least privilege** — ~~адмінка має Service Bindings, яких публічний застосунок не має~~.
   _Уточнено 11.09.2026: біндинги в обох оболонок **однакові** (тільки `API` → `api-dev`,
   у D1 немає ні та, ні та). Різниця не в доступі до даних, а в тому, які роути й який UI
   за ними стоять. Формулювання «least privilege» тут описує намір, не факт._

> **Раніше я пропонував об'єднати обидва застосунки в один білд і оцінював це в −5..7k рядків.
> Знімаю цю пораду.** Аргумент про витік адмінського коду в публічний бандл реальний, а
> TWA-застосунок вантажиться мільйонам користувачів. Роздільні origin'и тут — правильно.

**Отже, консолідація = одна кодова база + дві тонкі оболонки.**
Мета — прибрати дублювання *між* оболонками, не змінюючи модель деплою.

## 1. Стан фактів: оболонки вже майже ідентичні

Аудит показав, що різниці значно менше, ніж можна очікувати. Це добре — означає, що
консолідація це переважно видалення, а не переписування.

### Вже однакове (перевірено)

| Що | web-platform | web-admin |
|---|---|---|
| `src/App.tsx` | **байт-в-байт ідентичний** (`AuthGate` + `RouterProvider`) | те саме |
| `fixHtml`-плагін у `vite.config.ts` | ідентичний код | ідентичний код |
| React / react-router / zustand | 19.2.7 / 7.18.2 / 5.0.14 | **ті самі версії** |
| vite / tailwind / wrangler / typescript | 8.1.1 / 4.3.3 / 4.112 / ~6.0.2 | **ті самі версії** |
| `tsconfig.app.json` | `strict: true`, `noUnusedLocals` | те саме (різниця: platform має `@/*`) |
| CSS-фундамент | `@import "@wwwuabot/shared/styles/index.css"` + `tailwindcss` | те саме, той самий шрифт |
| `worker.ts` → `fixAssetHeaders()` | ідентична функція | ідентична функція |
| SPA через один воркер + ASSETS | так | так |

### Реально різне (і мусить таким лишитись)

| Вісь | web-platform | web-admin |
|---|---|---|
| Контекст входу | Telegram WebApp SDK | браузер |
| Auth | `X-Telegram-Init-Data` (HMAC на `BOT_TOKEN`) | cookie `admin_session` (HMAC на `ADMIN_SECRET`) |
| Роутинг | catch-all → `ScenarioPage` (сценарії з БД) | статичні роути: scenarios, users, sites, templates |
| D1-біндинг | немає | **немає** (зайвий бінд­инг прибрано 11.09.2026 — §5.2) |
| ASSETS-корінь | `./dist` | `./dist/client` |
| SPA-fallback | декларативний (`not_found_handling`) | ручний у `worker.ts` |

## 2. Правило межі (головне рішення)

Усе інше випливає з одного правила. Пропоную зафіксувати його в `AGENTS.md`:

| Шар | Можна ділити? | Куди |
|---|---|---|
| Типи, утиліти, токени, CSS | ✅ так | `packages/shared` |
| Рендеринг блоків і сторінок (`PageRenderer`) | ✅ так | `packages/ui` |
| Транспорт API (`apiFetch`) | ✅ так | `packages/shared` |
| Перевірка сесії (HMAC, cookie, initData) | ✅ так, як **чиста функція** | `packages/shared` |
| AuthGate (оболонка рішення) | ❌ ні | окремо в кожному застосунку |
| Роутер, `worker.ts`, `wrangler.toml` | ❌ ні | окремо |
| Редакторські UI адмінки | ❌ ні | `web-admin-dev` |

**Ключове розмежування:** *логіка перевірки* — спільна; *рішення, що робити при провалі* — своє
в кожного (TWA показує «відкрийте в Telegram», адмінка — `LoginScreen`).
