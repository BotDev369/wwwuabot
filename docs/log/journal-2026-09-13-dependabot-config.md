# 13.09.2026 — `dependabot.yml`: теки-привиди і групування оновлень

**Коміти `7f9a856` (привиди) і наступний (групи)** · CI — див. §0 плану.

Один запис на одну тему: конфіг Dependabot. Записи про тести домену `sites` — окремо
([`journal-2026-09-13-sites-tests.md`](./journal-2026-09-13-sites-tests.md)).

## 1. Теки-привиди

Конфіг перелічував `/bot`, `/web`, `/api`, `/web-admin` — таких тек у репозиторії **немає**
(воркспейси звуться `*-dev`). Dependabot недосяжну теку просто пропускає, тож шкоди не було,
але читалось це як покриття, якого немає: оновлення `wrangler` у воркерах виглядали «не
описані ніде».

Доказ, що кореневого запису достатньо: **PR #45** змінював `api-dev/package.json`,
`bot-dev/package.json`, `web-platform-dev/package.json`, `web-admin-dev/package.json` — тобто
`directory: "/"` працює з усіма воркспейсами одного npm-локфайла. Окремий запис знадобиться
лише тоді, коли воркспейс отримає власний lockfile; інакше це дало б дублікати PR на ту саму
залежність.

## 2. Групування: 11 PR → 1–2 на тиждень

13.09.2026 Dependabot відкрив 11 PR поспіль — кожен на один пакет (#46–#51 і старші).
Переглянути такий список із телефона неможливо, а гілки швидко відстають від `main` і починають
конфліктувати в `package-lock.json` — саме так «зависав» PR #42 (розібрано в записі про типи
`node`).

Тепер у кореневого запису (npm) і в запису `github-actions` є по одній групі:

```yaml
    groups:
      npm-minor-and-patch:
        applies-to: version-updates
        update-types:
          - "minor"
          - "patch"
```

**Що лишається окремими PR — свідомо:**

- **мажорні** версії: у них ламаючі зміни, рішення мусить бути усвідомленим (`typescript 7`
  вимагав міграції `tsconfig`, `vitest 5` — виправлення типів `node`, `checkout@v7` — Node 24);
- **оновлення безпеки**: `applies-to: version-updates`, а не `security-updates`, — уразливість
  не має чекати тижневого циклу групи.

**Плата за групування (чесно):** якщо в згрупованому PR впаде один пакет, червоним стане весь PR,
і решту оновлень не можна буде влити окремо. Escape hatch документований:
`@dependabot ungroup` у PR — Dependabot розкладе його назад на окремі гілки.

## 3. Звірка зі схемою, а не «на пам'ять»

Синтаксис перевірено справжнім YAML-парсером (Prettier), структуру — розбором у AST
(`prettier.__debug.parse`): обидва ідентифікатори груп і значення `version-updates`, `minor`,
`patch` присутні в дереві. Самі значення звірено з офіційним довідником
[Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference):

- `groups.<IDENTIFIER>` — мусить починатись і закінчуватись **літерою** (тут так);
- `applies-to` — `version-updates` / `security-updates`;
- `update-types` **у групах** — `minor` / `patch` / `major`. Це не те саме, що `update-types`
  у `allow`/`ignore`, де значення мають вигляд `version-update:semver-minor`. Найлегше
  помилитись саме тут, і помилка була б тихою: конфіг валідний, група просто нічого не ловить.

## Перевірка

- `npx prettier --check .github/dependabot.yml` — YAML валідний;
- AST містить `npm-minor-and-patch`, `actions-minor-and-patch`, `version-updates`, `minor`, `patch`;
- `check:docs` — посилання живі, документів 43, мертвих 0.

**Чого перевірка не доводить:** що групи реально спрацюють — це видно лише на наступному запуску
Dependabot (тижневий розклад). Ознака успіху: замість пачки PR на один пакет приходить один
`Bump the npm-minor-and-patch group` із кількома залежностями. Якщо замість цього прийде
11 окремих PR — групування мовчки не застосувалось (відомі issue у `dependabot-core` про
ігнорування `update-types`), і тоді конфіг треба правити заново, а не вважати питання закритим.
