# Контент в одній таблиці: `pages` + міграція

> ⚠️ **Скасовано того ж дня.** Таблицю `pages` і міграцію до неї прибрано: на дев-базі вона
> ніколи не існувала, читача не мала, а дані в ній були б ті самі, що вже в `scenarios`.
> Актуальний стан — [`../CONTENT_MODEL.md`](../CONTENT_MODEL.md); чому саме так —
> [`journal-2026-09-13-drop-pages-table.md`](./journal-2026-09-13-drop-pages-table.md).
> Запис лишено як історію: обидві вади, які він описує, були справжні.

**Дата:** 13.09.2026 · **рішення власника:** «4 таблиці → 1»

Чотири таблиці описували те саме — сторінку контенту. Цей запис фіксує, що зроблено,
як це перевірено **на справжньому SQLite** і, головне, які дві вади знайшлись дорогою:
обидві були невидимі для компілятора, тестів і гейтів.

## Вада 1: індекси в SQLite мають **глобальні** імена

`idx_pages_slug` вже належав `site_pages`. Тому моє

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_pages_slug ON pages(kind, parent_id, slug)
```

не помилка й не попередження — **порожня дія**. `pages` лишилась без унікальності адреси,
і два рядки спокійно дістали той самий `slug`. Знайшлось не розумом, а запитом до
`sqlite_master`: індекс `idx_content_slug` був відсутній, хоч «схема повна».

Виправлено двічі: індекси `pages` звуться `idx_content_*`, а раннер після застосування
звіряє **і таблицю-власника** кожного індексу — не лише ім'я. Інакше та сама пастка
повторилась би з наступним іменем.

## Вада 2: `NOT EXISTS` бачить базу **до** вставки

```sql
INSERT INTO pages (...) SELECT ... FROM scenarios s
WHERE NOT EXISTS (SELECT 1 FROM pages p WHERE p.slug = <адреса s>)
```

Два вихідні рядки з однаковою адресою (`web_slug` у сценаріїв ніколи не був унікальним)
проходять цього охоронця **обидва**, і далі `UNIQUE`-індекс валить **усю** інструкцію —
міграція не переносить нічого. Тому кожна з чотирьох інструкцій спершу ранжує адреси
(`ROW_NUMBER() OVER (PARTITION BY slug …)`) і бере одного представника: того, чий `codeword`
і є адресою. Решта — у звіт.

## Перевірка: не «має працювати», а прогін на SQLite

Локальний D1 працює **без логіну** в Cloudflare — саме на ньому й перевірялось:

```bash
node scripts/migrate-content.mjs --persist .tmp-d1-check      # схема + перенос
npx wrangler d1 execute DB --config api-dev/wrangler.toml --local \
  --persist-to .tmp-d1-check --file .tmp-d1-seed.sql          # легасі-дані
node scripts/migrate-content.mjs --persist .tmp-d1-check      # перенос на даних
```

Сіяні дані покривали саме небезпечні випадки: головна `__base__` зі `web_slug = '/'`,
`is_active = 0`, порожній `page_data`, два сценарії з **однаковою** адресою, адмінський
рядок із **тим самим** `codeword`, сайт зі `settings.navigation`, опублікована й чернеткова
сторінки сайту. Результат:

| Перевірка | Результат |
|---|---|
| Доїхало | `scenarios` 3/4, `scenarios-admin` 1/2, `sites` 1/1, `site_pages` 2/2 |
| Пропущені — названі у звіті | `scenarios dup` (чужа адреса), `scenarios-admin mydate` (чужий `codeword`) |
| Легасі-таблиці | не змінені: 4 / 2 / 1 / 2 рядки на місці |
| Повторний запуск | ті самі числа, `pages` = 7 рядків, дублів адрес 0 |
| Схема | 21 об'єкт із реєстру; `idx_content_slug` належить `pages` |
| Вкладеність JSON | `bot.rich_data[0].type = 'text'` — тобто JSON лишився JSON, а не рядком |

## Чого цей крок **не** робить

**Читачі ще на старих таблицях.** `pages` заповнена (на деві — після першого запуску), але
ні бот, ні платформа, ні адмінка її не читають: перемикання — окремий крок, і робити його
треба разом із записом, інакше редактор пише в одне, а рендер читає інше. Фази —
[`../CONTENT_MODEL.md`](../CONTENT_MODEL.md) §4.

**Міграція не запускалась на деві.** У середовищі розробки немає доступу до D1
(`wrangler whoami` → не залогінений). Потрібен `CLOUDFLARE_API_TOKEN` (див. `DATA_MODEL.md`).

**Дві головні сторінки.** У сценаріїв їх дві: `__base__` (платформа, `web_slug = '/'`) і
`main` (бот, `/start` без параметра). Міграція переносить `__base__` як головну
(`slug = ''`), а `main` — як звичайну сторінку: зливати чийсь контент вона не має права.
Об'єднати їх — правка **читача** (у новій моделі `/start` без параметра відкриває головну),
і зробити це треба в фазі 3, коли читачі переїдуть на `pages`.
