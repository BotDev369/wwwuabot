# Таблиця `scenarios-admin` — видалено, а не перенесено

**Дата:** 13.09.2026 · **Тема:** четвертий «контейнер» одного контенту виявився тестовою копією
· **Стан:** фаза 2.5 плану `docs/CONTENT_MODEL.md` · **Попередній крок:**
[`journal-2026-09-13-share-deeplink.md`](./journal-2026-09-13-share-deeplink.md)

## Що сказав власник

> «Нам більше не потрібна таблиця сценарії-адмін, то був тест. Видаляємо її у весь функціонал
> пов'язаний з нею. Дані там неважливі.»

Доти я тримав її в плані як **джерело міграції**: переносив у `pages` зі `status = 'draft'`
(«переносимо, бо це чиясь робота»). Це було обережно — і хибно: обережність до нічийого контенту
коштувала таблиці, яку не читав ніхто, цілої інструкції переносу й гілки в кожному шарі.

## Що видно з коду, а не з наміру

| Питання | Відповідь |
|---|---|
| Хто читав `scenarios-admin`? | тільки адмінка — шість маршрутів `/api/admin/scenarios/*` |
| Хто ще? | **ніхто**: ні бот, ні платформа, ні публічний API |
| Де вона була оголошена? | у реєстрі таблиць, власна копія DDL на 23 колонки |
| Що її відрізняло від `scenarios`? | нічого, крім того, що редактор мав дві вкладки |

Тобто це не «другий контент», а **друга копія того самого з єдиним споживачем — тим, хто її ж і
редагував**. Саме тому видалення нічого не ламає: не існує другого читача, якого треба перевчити.

## Що зникло (повний перелік)

| Шар | Було | Стало |
|---|---|---|
| Схема | оголошення `scenarios-admin` у реєстрі | немає; `check:db` бачить **8** таблиць замість 9 |
| API | `scenarios-admin.controller.ts` + шість маршрутів | маршрутів немає; 404 — як і для будь-якого невідомого шляху |
| Фабрика | `createScenariosController({ table })` з типом `ScenarioTableName` | **злита** в `scenarios-portal.controller.ts`: фабрика з одним покупцем — порожня ланка |
| Адмінка | вкладка «Адмін», `ScenarioTable` у кожній із семи функцій API, `table` у сторі й картці | один префікс `/api/portal/scenarios`, параметр `table` прибрано всюди |
| Іконка | `icons["scenarios-admin"]` (шестерня) | прибрана — нею користувалась лише ця вкладка |
| Модель контенту | `ContentSource` з трьома значеннями, `source` — аргумент адаптера | два значення; адаптер сценарію більше не приймає джерело |
| Міграція | 4-та інструкція `INSERT … FROM "scenarios-admin"`, рядки `sa:` у звіті | 3 інструкції; звіт рахує три джерела, запит «діплінк змінився» — теж |
| Тести | 2 перевірки на admin-джерело | прибрані; решта — зелені (332 у 34 файлах) |

**Чому зникла саме фабрика.** Її єдиним призначенням було «дві таблиці з ідентичною схемою не
мають розходитись». З однією таблицею вона не захищала нічого: лишалась би шаром, через який
треба пройти, щоб побачити, що таблиця одна.

## Що **не** зникло

- **`pages`** — єдине сховище контенту, оголошене в реєстрі. Цей крок її не чіпає.
- **`scenarios`, `sites`, `site_pages`** — легасі-джерела міграції. Вони лишаються до фази 3–4:
  доки читачі не переїхали на `pages`, видаляти їх означало б зламати робочий продукт.
- **Міграція** — тільки `INSERT`; жодного `DELETE`/`DROP` не додано. Перевірка в тесті
  (`безпека міграції`) стежить за цим і далі.

## Перевірка

Сіянина легасі-даних на **справжньому SQLite** → міграція → перевірка запитами:

```
scenarios 3/3 · sites 1/1 · site_pages 1/1      — усі рядки доїхали
price_list → price-list                          — нормалізація `_` → `-` у звіті
2-й запуск: ті самі числа                        — ідемпотентність
19 об'єктів схеми з реєстру на місці             — схема повна
```

| | |
|---|---|
| Тести | **332** у 34 файлах |
| Гейти | typecheck · lint · format · `check:css` · `check:quality` · `check:docs` · `check:db` — усі зелені |
| `check:db` | 8 таблиць: `mydate_analysis`, `pages`, `scenarios`, `settings`, `site_pages`, `sites`, `templates`, `users` |

## Що потрібно від власника

Реєстр прибрав **створення** таблиці, але на вже заведеній дев-базі вона лишається: `ensureTables`
ніколи не робить `DROP` — інакше схема залежала б від того, який воркер запустився першим.
Одна команда з машини, де `wrangler` залогінений:

```bash
npx wrangler d1 execute DB --config api-dev/wrangler.toml --remote --yes \
  --command 'DROP TABLE "scenarios-admin";'
```

Порядок із міграцією значення не має: `npm run migrate:content` цієї таблиці вже не торкається —
ні на читання, ні у звіті.
