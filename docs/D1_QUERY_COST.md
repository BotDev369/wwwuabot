# D1: що читається за тиждень

Загальна картина витрат Cloudflare — [`CLOUDFLARE_AUDIT.md`](./CLOUDFLARE_AUDIT.md). Тут — лише
`rows_read`: хто саме читає рядки, скільки й чому. Числа виміряні 09.11.2026 за 02.11–09.11.

## 1. Звідки числа

Cloudflare GraphQL, датасет `d1QueriesAdaptiveGroups`: він має вимір `query` (сам текст запиту) і
`sum.rowsRead`. Це єдине джерело, яке називає винуватця поіменно; `d1AnalyticsAdaptiveGroups` дає
лише суму по базі й за той самий тиждень показує 1 367 254 рядки проти 1 556 507 тут — різні
датасети й різна затримка, тому змішувати їх не можна. Аналітика відстає приблизно на добу: свіжі
запити поточного дня в ній ще не видні.

Повторний зріз — `npm run audit:cloudflare` (тиждень за замовчуванням, `-- --days=14` для довшого вікна):
той самий запит до всіх чотирьох датасетів за один запуск.

```graphql
{ viewer { accounts(filter: {accountTag: "…"}) {
  d1QueriesAdaptiveGroups(limit: 500, filter: {date_geq: "2026-11-02", date_leq: "2026-11-09"}) {
    count sum { rowsRead rowsReturned queryDurationMs } dimensions { query }
} } } }
```

## 2. Тиждень: 29 975 запитів і 1,55 млн рядків

Пік — 04.11: 5 270 запитів і 895 800 рядків. Це **не сторінки** (вони після C3 читають по 4 рядки),
а дашборд витрат адмінки.

| Запит | Рядків | Виконань |
| --- | --- | --- |
| `GROUP BY recipt_edrpou` | 320 841 | 180 |
| `GROUP BY payer_edrpou` | 255 827 | 143 |
| `GROUP BY kekv` | 216 080 | 74 |
| `GROUP BY budget_code` | 156 762 | 54 |
| `COUNT/SUM` без групування | 66 193 | 37 |
| `MIN/MAX trans_date` | 51 881 | 29 |
| `GROUP BY kpk` | 47 584 | 16 |
| `INSERT INTO user_events` | 25 200 | 1 050 |

Усі ці запити разом — **82 %** тижневих `rows_read`. Таблиця `spending_transactions` має 1 789
рядків, а один `GROUP BY` читає ≈2 900 — тобто більше за таблицю.

## 3. Чому більше за таблицю

План (`EXPLAIN QUERY PLAN`) для розрізу за `kekv`:

```
SCAN spending_transactions
USE TEMP B-TREE FOR GROUP BY
USE TEMP B-TREE FOR ORDER BY
```

Індекси в таблиці — `(payer_edrpou, trans_date)` і `(recipt_edrpou, trans_date)`; за `trans_date`
індексу немає, тож фільтр за датою не звужує нічого й таблиця читається повністю. Далі два
тимчасові b-tree: один на групування, другий на сортування за сумою. `rows_read` рахує рядки
**всіх** цих структур — тому ≈1,6× від таблиці на запит.

## 4. Чому індекс — не лікування

- **`(trans_date)`** прибрав би скан для `MIN/MAX`, але не для розрізів: групуванню потрібні
  `kekv`, `kpk`, `budget_code`, `payer_edrpou`, `recipt_edrpou` і `amount`, яких в індексі немає, —
  SQLite пішов би в таблицю за кожним рядком і прочитав би ті самі рядки двічі.
- **Покривні індекси на кожен розріз** — це п'ять індексів заради ≈30 % (скан зникає, але тимчасові
  b-tree лишаються) і плюс запис при кожному оновленні з Є-data.

## 5. Що лікує — і чому зараз не робиться

Один прохід: прочитати рядки вікна (1 789) із потрібними колонками й згорнути всі розрізи в пам'яті
в одному місці. Це ≈1 789 рядків на показ замість ≈29 000, тобто **≈16×** менше, і виграш росте
разом із таблицею.

Зараз не роблю свідомо: пік — **14 %** добової квоти, показів дашборда ≈44 на тиждень, а самі запити
дешеві за часом (386 мс на 180 виконань розрізу за `recipt_edrpou`). Повертатися, коли
`spending_transactions` виросте на порядок або дашборд стане щоденним.
