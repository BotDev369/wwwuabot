## 0. Що тут означає «консолідація»

Це **не** злиття двох воркерів в один. Рішення про роздільні воркери вже затверджене в
[PAGE_ENGINE_ARCHITECTURE.md](./PAGE_ENGINE_ARCHITECTURE.md) (09.09.2026) і має обґрунтування,
яке я перевірив і вважаю слушним:

1. **Zero bundle leakage** — адмінський JS фізично не потрапляє в бандл користувача.
   _Перевірено: це правда вже сьогодні, бандли окремі._
2. **Same-Origin Policy** — адмінська cookie не читається з публічного домену.
   _Перевірено: хости різні (обидва на `*.workers.dev`; власних доменів немає)._
3. **Cloudflare Access** — edge-захист адмінки не існує, якщо об'єднати.
   _Уточнено 12.09.2026: Access на адмінці **поки не налаштований** — це аргумент на
   користь роздільних воркерів, а не опис поточного захисту. Єдиний барʼєр зараз —
   cookie `admin_session` + адмін-гейт в `api-dev`._
4. **Least privilege** — ~~адмінка має Service Bindings, яких публічний застосунок не має~~.
   _Уточнено 11.09.2026: біндинги в обох оболонок **однакові** (тільки `API` → `api-dev`,
   у D1 немає ні та, ні та). Різниця не в доступі до даних, а в тому, які роути й який UI
   за ними стоять. Формулювання «least privilege» тут описує намір, не факт._

> **Раніше я пропонував об'єднати обидва застосунки в один білд і оцінював це в −5..7k рядків.
> Знімаю цю пораду.** Аргумент про витік адмінського коду в публічний бандл реальний, а
> TWA-застосунок вантажиться мільйонам користувачів. Роздільні origin'и тут — правильно.

**Отже, консолідація = одна кодова база + дві тонкі оболонки.**
Мета — прибрати дублювання *між* оболонками, не змінюючи модель деплою.

## 2. Правило межі (головне рішення)

Усе інше випливає з одного правила. Пропоную зафіксувати його в `AGENTS.md`:

| Шар | Можна ділити? | Куди |

### 5.3. ⛔ Ідентичності користувача не перевіряють — ЗНАЙДЕНО Й ПІДТВЕРДЖЕНО 11.09.2026

Це найважливіша знахідка аудиту. Авторизації користувача фактично немає.

**а) 16 хендлерів сайтів беруть особистість із непідписаної cookie.**

`getUserIdFromRequest()` — три ідентичні копії:
`sites.controller.ts:39`, `site-pages.controller.ts:34`, `templates.controller.ts:32`:

```ts
/** Витягує userId з cookie (HMAC auth). */
function getUserIdFromRequest(request: Request): number | null {
  const match = (request.headers.get("Cookie") ?? "").match(/user_id=(\d+)/);
  if (match) return parseInt(match[1], 10);
  return null;
}
```

Коментар каже «HMAC auth», але HMAC тут немає — це просто читання числа з cookie.

**б) Цю cookie ніхто і ніколи не ставить.** У всьому репозиторії єдиний `Set-Cookie` —
це `admin_session` в `auth.controller.ts`. Наслідки два, і обидва погані:

- **Зараз:** усі 16 хендлерів завжди повертають 401 — **фіча «сайти» мертва.**
- **Якщо cookie колись з'явиться:** будь-хто виставляє собі `user_id=1` і керує
  чужими сайтами, сторінками й шаблонами.

**в) `my-dates` приймає непідписаний `X-Telegram-User-Id`.**
`my-dates.controller.ts:114-134`: якщо `X-Telegram-Init-Data` є — перевіряється підпис;
якщо немає — береться голий числовий заголовок і код сам це логує:
`"unsigned X-Telegram-User-Id accepted"`. Тобто достатньо не надіслати initData, щоб
читати й писати чужі дати.

**г) `/api/user/profile?user_id=N` — публічний, без авторизації.**
`users.controller.ts:222-250` бере `user_id` з query-параметра і віддає `role`, `tariff`,
`status`, `discount`, `permissions`. Тобто будь-хто дізнається тариф і права будь-якого
користувача.

**д) `AuthGate` платформи — це перевірка браузера, не сервера.**
`web-platform-dev/src/app/AuthGate.tsx` робить лише
`!!window.Telegram?.WebApp?.initDataUnsafe?.user?.id`.

**е) Тестів на auth — нуль.**

**Дія:** одна довірена ідентичність — **тільки підписаний `initData`** (`verifyInitData`).
Відхиляти `X-Telegram-User-Id`, прибрати непідписану cookie, `/api/user/profile` має брати
`user_id` з перевіреного підпису, а не з query. Разом із сервером правиться клієнт
(надсилати `initData` у кожному запиті) — інакше сайти лишаться мертвими.

> **ЗАКРИТО 11.09.2026.** Єдина точка правди — `api-dev/src/shared/identity.ts`:
> `user_id` береться ТІЛЬКИ з підписаного `initData`. Непідписану cookie, голий
> `X-Telegram-User-Id` і `?user_id=` в `/api/user/profile` прибрано. Регресійні

### 5.6. `/api/mydate/*` — публічний запис у БД і KV

Ці ендпоїнти не перевіряють ідентичність — і це **правильно**: це калькулятори
(нумерологія, астрологія) з кешем по даті, а не персональні дані. Але разом із
читанням вони виконують `saveAnalysis()` — тобто **хто завгодно може писати в БД і KV**
довільними датами.

Це не витік даних, а питання ресурсів: спамер може наповнити `CONTENT_KV` і таблицю
аналізів. Захист від цього — або rate-limit, або вимога `initData` (він є в Mini App
у будь-якому разі).

**Дія: відкладено до появи реального трафіку.** Перед публічним запуском вирішити:
`initData` (простило) чи Cloudflare Rate Limiting (дешевше за CPU). Зараз будь-який
захист тут дорожчий за ризик.

**Статус:** відкрито, свідомо відкладено.

### 5.7. S-6: CI не гейтив нічого, крім лінта й типів

`.github/workflows/deploy.yml` мав три тихі дірки — саме ті, які найдорожчі
для проєкту, що збирається в прод:

| Було | Наслідок |
|---|---|
| Тести не запускались у CI взагалі (S-6) | 111 тестів писались, але червоний тест не заважав деплою |
| `npm audit` стояв з `continue-on-error: true` | критична CVE у залежностях їхала в прод мовчки |
| `npm install` замість `npm ci` | збірка не була відтворюваною: патч транзитивної залежності змінював прод без жодного коміту |

Плюс дві менші: два пуші поспіль давали **паралельні деплої** (Cloudflare —
last-write-wins, тож старіший коміт міг лягти поверх новішого), і
`GITHUB_TOKEN` мав дефолтні права, хоча деплою він не потрібен.

**Дія:** єдина блокуюча джоба `checks` перед усіма деплоями; `npm ci`;
`npm audit --audit-level=critical` без `continue-on-error`; `npm test`;
тригер `pull_request` (тільки гейти — деплой з PR неможливий через
`github.event_name != 'pull_request'`); `concurrency` із чергою замість
скасування; `permissions: contents: read`.

> **ЗАКРИТО 11.09.2026.** `npm audit --audit-level=critical` проходить
> (у залежностях 6 вразливостей, але всі — moderate/high від ланцюжка
> `wrangler`/`miniflare`). Поріг свідомо лишено на `critical`: на `high`
> деплой блокувався б зараз, а `--force` вимагає мажорних оновлень wrangler.
>
> **ЗАКРИТО 12.09.2026.** Виконано саме в тому порядку, як було записано: спочатку

### 5.8. Моніторинг: про падіння воркера дізнавались від користувачів

**Статус:** код зроблено 11.09.2026; зовнішній монітор підключає власник акаунта.

Після закриття безпекового боргу лишалось три сліпі зони:

| Зона | Що це означало на практиці |
|---|---|
| Немає зовнішньої uptime-перевірки | якщо воркер лягав, першими про це дізнавались користувачі, а не ми |
| `/health` перевіряв лише сам воркер | він не торкався D1/KV, тож віддавав `status: "ok"` навіть при мертвій базі — фальшиве заспокоєння |
| Логи | `[observability]` був відсутній у `api-dev`, `web-platform-dev`, `web-admin-dev`; `bot-dev` мав лише `[observability.logs]` без top-level `enabled` |

**Дія 1 — два різні health-ендпоїнти.** Це дві різні відповіді, і змішувати їх не можна:

| Ендпоїнт | Питання, на яке відповідає | Залежності |
|---|---|---|
| `GET /health` | «воркер живий?» | не торкається БД і KV |
| `GET /health/deep` | «дані працюють?» | `SELECT 1` у D1 + `get` у KV; **503**, якщо хоч одна недоступна |

`/health/deep` навмисно **не** повертає текст помилки: ендпоїнт публічний, а
повідомлення D1 бувають детальними (назви таблиць, колонок, SQL). Текст іде в лог
(`apiLog.error`), назовні — лише `checks: { db, kv }`. Обидві відповіді з
`Cache-Control: no-store`, інакше монітор бачив би закешований стан.

**Дія 2 — Workers Logs у всіх 4 воркерах.** Однакова конфігурація:

```toml
[observability]
enabled = true

[observability.logs]
enabled = true
invocation_logs = false
```

`invocation_logs = false` вимикає лише службовий лог кожного запиту (найбільший обсяг,
найменша користь); власні `console.*` та необроблені винятки лишаються — саме тому
безкоштовного ліміту (200 000 подій/добу, зберігання 3 дні) вистачає з запасом.

**Дія 3 — зовнішній монітор (робить власник акаунта).** UptimeRobot, безкоштовний
план: 50 моніторів, перевірка раз на 5 хвилин, без картки. Монітор — HTTP(s) на
`https://api-dev.diskomate.workers.dev/health/deep`, бо саме він падає (503), коли
лежить база, а `/health` на цю роль не годиться.

**Дія 3 — Sentry (зроблено 11.09.2026).** UptimeRobot каже, **що** впало, а Sentry —
**чому**. SDK `@sentry/cloudflare` під'єднано у `api-dev` і `bot-dev`; опції живуть у
спільному `@wwwuabot/shared/observability/sentry`, тож політика даних описана один раз:

| Рішення | Чому саме так |
|---|---|
| `sentryOptions()` вертає `undefined` без `SENTRY_DSN` | деплой без секрету безпечний, а вмикається Sentry одним секретом — без зміни коду |
| `tracesSampleRate: 0` | перформанс зʼїдав би квоту (5 000 помилок/міс), не даючи користі |
| `dataCollection` вимкнено + `beforeSend` ріже заголовки/cookie/тіло/query | у заголовку їде Telegram `initData` (ним можна видати себе за користувача, поки підпис не сплив), у cookie — `admin_session` |
| `withSentry` — єдина обгортка в `index.ts` воркера | необроблені винятки ловляться без try/catch у кожному контролері |
| Явний 500 в `api-dev` | раніше клієнт отримував сирий stack trace Cloudflare; тепер — `{"error":"Internal error"}`, а деталі йдуть у логи й Sentry |
| `bot.catch` звітує сам | помилки, які grammY перехоплює, до `withSentry` не долітають |
| `[version_metadata]` у `wrangler.toml` | у Sentry видно, який саме деплой зламався |

**Без залежностей у shared:** модуль не імпортує SDK у рантаймі — віддає звичайний обʼєкт,
а сумісність із реальним типом перевіряє `satisfies Sentry.CloudflareOptions` на місці
виклику. Так `packages/shared` не тягне серверний SDK у браузерні бандли. Саме цей
`satisfies` одразу й зловив розходження в сигнатурі `beforeSend`.

**Чому не в `web-platform-dev` / `web-admin-dev`:** там помилки живуть у браузері, і DSN
треба вшивати в бандл при збірці (окремий механізм — секрет GitHub Actions + `VITE_`).
Окремий крок, коли з'явиться трафік.

**Поза кодом:** власник акаунта створює проєкт у Sentry і додає секрет `SENTRY_DSN` у
Cloudflare для `api-dev` і `bot-dev` — інструкція в `docs/MONITORING.md`.

**Перевірка:** `health.controller.test.ts` (7 тестів) фіксує найдорожче — 503 при
мертвій D1 і при мертвому KV, відсутність витоку тексту помилки, рівно один запит
до БД, `no-store`.
