# Планка якості в CI

**Гейт:** `npm run check:quality` (`scripts/check-quality.mjs`) · **крок у CI:** джоба `checks`,
поряд із `check:css`, `check:docs` і `check:db` · **леджер боргу:** `scripts/quality-baseline.mjs`

Гейти перевіряли, що код **компілюється**, а не що він потрібен. Цей крок перетворює правила з
тексту на крок збірки: рецензент бачить diff, а не файл, який виріс із 200 рядків до 400 за десять
комітів.

## Чотири правила

| # | Правило | Джерело | Що вважається порушенням |
|---|---|---|---|
| 1 | **Кристалева ясність** | `AGENTS.md` §3 | файл > 400 рядків — помилка; > 200 — попередження |
| 2 | **Нативні діалоги** | `AGENTS.md` §4 | будь-який `alert` / `confirm` / `prompt` (і `window.…`) |
| 3 | **Висота екрана** | `AGENTS.md` §3 | `100vh` без `100dvh`-фолбеку поруч |
| 4 | **Емодзі в UI** | `AGENTS.md` §4 | піктограма в коді UI замість `<Icon />` |

- `dialog.alert(…)` (наш спільний діалог) і оголошення методів у `packages/ui/src/dialog/`
  порушеннями не є — перевірка це знає.
- **Дані — не логіка.** Файли з таблицями констант (`icons.tsx`) ліміт рядків не рахують взагалі:
  дробити `icons.tsx` навпіл — шкодити.
- **Символи ≠ емодзі.** `↑ ↓ ✕ ★ ✓ ♑` забороні не підлягають: це типографіка. Перевірка ловить
  саме піктограми (діапазон `U+1F000–U+1FAFF` і селектор варіації `U+FE0F`), інакше вона
  «забороняла» б зодіакальні знаки в контенті.
- **Тексти бота** (`bot-dev/src/shared/config/texts.ts`) — поза перевіркою на емодзі: це
  контент, який малює Telegram, а не UI оболонки, тож `<Icon />` там немає й бути не може.

## Бюджет розміру: у коду й документації свої межі

Правило кристалевості одне, але міра в кожного жанру своя — код і документ читають по-різному,
тож і ліміт стоїть окремо: код тримає `check:quality`, документи — `check:docs`.

| Група | М'яка межа (попередження) | Жорстка (помилка) | Де право на більше |
|---|---|---|---|
| Код | 200 рядків | 400 рядків | `scripts/quality-baseline.mjs` — леджер боргу, тільки зменшується |
| Документ | 200 рядків **або** 24 KB | 400 рядків | `BUDGET_RIGHTS` у `scripts/check-docs.mjs` — кожне право з причиною |

Чому право — це записана причина, чому вага рахується разом із рядками, чому генеровані документи
розмір не нормують і чому межа стоїть нижче за реальну шкоду — [`README.md`](./README.md).

**Межа редагування — окрема стеля.** Інструменти беруть лише перші ~35 KB файлу: довший документ
**читається**, але правка в хвості «не знаходить» текст — і не скаржиться. Тому `check:docs` вважає
**помилкою** файл понад 34 KiB (34 816 байтів), а не попередженням: це межа інструмента, а не смак.
Файл, який її переріс, ділиться на теми — або, якщо поділ справді попереду, стає в `EDIT_LIMIT_DEBT`
із причиною. Леджер живий: щойно файл вписується в межу, гейт вимагає прибрати рядок. Так поділено
`docs/SHOPS.md` (товар — [`PRODUCTS.md`](./PRODUCTS.md)) і `docs/DESIGN_SYSTEM.md` (знаки —
[`ICONS.md`](./ICONS.md), каркас оболонки — [`PLATFORM.md`](./PLATFORM.md)).

## Реєстр гейтів

| Гейт | Що ловить |
|---|---|
| `npm run check:quality` | моноліти, нативні діалоги, голий `100vh`, емодзі в UI; борг — `scripts/quality-baseline.mjs` |
| `npm run check:css` | клас у розмітці без правила (помилка) і правило без розмтки (попередження); борг — `scripts/css-baseline.mjs` |
| `npm run check:docs` | бюджет документів, мертві посилання й шляхи, згадки з коду, `AGENTS.md §N`, покажчик, секційний бюджет, свіжість `API.md` |
| `npm run check:comments` | блок коментаря, який уже є розділом документа, і мертвий шлях у коментарі; борг — `scripts/comment-baseline.mjs` |
| `npm run check:bundle` | вага клієнтського бандла оболонки понад ліміт у gzip; ліміти — `scripts/bundle-baseline.mjs`; перед запуском потрібні зібрані `dist/` обох оболонок |
| `npm run check:db` | шість кроків: розходження реєстру й DDL, `CREATE TABLE` поза реєстром, неоголошена таблиця в SQL, `ensureTables` поза реєстром, `SELECT *` із важкою колонкою (`users`) поза рядком за ключем, реєстр без читачів |
| `npm test` | поведінку, включно з `*.dom.test.*` (див. нижче) |
| `npm run check:coverage` | падіння покриття нижче підлоги й новий код без покриття; підлоги — `scripts/coverage-baseline.mjs` |

Чого гейт не ловить і не може: правило, яке суперечить двом іншим правилам, і
коментар, який переказує код. Сутність правила людський текст — механіка ловить
лише те, що можна виміряти.

## Леджер боргу

Два леджери, і в кожного те саме правило: сюди потрапляє **лише те, що вже
описано в документації як відкрита робота**. Усе інше — нова помилка, і крок
`checks` її зупинить.

`scripts/quality-baseline.mjs` — файли коду, що перейшли межу рядків.

`scripts/comment-baseline.mjs` — коментарні блоки, довші за абзац документа: правило
«пояснення живе в `docs/`» ([`COMMENTS.md`](./COMMENTS.md)). Число може лише меншати,
і зменшення теж падає — час зменшити базу.

**Леджер не можна забути оновити:** якщо файл із нього зник із чекауту або вже вписався в ліміт,
перевірка впаде й попросить прибрати рядок. Так борг не може «висіти в списку» після того, як
його закрили.

## Підлога для нового коду

Загальна підлога ловить просідання, але не ловить **приріст без тестів**: додали
200 рядків і один тест — середнє знизилося на трохи, і гейт мовчить. Тому в
`scripts/coverage-baseline.mjs` є ще одна пара: `NEW_CODE_SINCE` (коміт, з якого
починається «новий код») і `NEW_CODE_FLOOR` (відсоток рядків, нижче якого новий
файл не проходить). `npm run check:coverage` бере зміни через
`git diff <NEW_CODE_SINCE>` разом із непростеженими файлами, тож правило діє ще
до коміту, і в CI потрібен checkout із `fetch-depth: 0`.

Список «каталогів без тестів» свідомо **не** заводили: на момент введення таких
було 66, через рік список із 66 адрес був би брехнею. Натомість коміт у базі —
це рухомий **борг**: щоразу, коли черговий старий модуль набирає тестів, база
зсувається вперед і вимога переходить до наступного. Два винятки гейт не
торкається: файли-дефолти й помічники без гілок (`NEW_CODE_MIN_STATEMENTS` — заради
нуля assertions не потрібні) і файли, у яких після бази змінилися **лише
коментарі** — правило про новий код не має права вимагати тестів там, де хтось
дописав два рядки пояснення до старого файлу.

Де саме проходить межа боргу зараз — каже `AGENTS.md` §8 («відкрита робота»); тут
лишається саме правило, а не перелік файлів, який старіє першим.

## Тести з браузером — окремим кроком

`vitest.config.ts` тримає `environment: "node"`: тести не мають `document`, тож серверний рендер
(`renderToStaticMarkup`) бачить **який HTML**, але не бачить **що станеться після дотику** — ані
`useEffect`, ані `localStorage`. Тому поведінка під дотиком (закриття меню поза, запис вибору в
пам'ять пристрою) була неперевірена: саме в ній жив баг «тема не застосовується».

Тести з браузером вмикаються **лише для свого файлу** — інакше зміниться середовище для всіх
решти, а в коді є свідомі охоронці `typeof document === "undefined"` (`theme-dom.ts`,
`font-dom.ts`):

```ts
// @vitest-environment jsdom
```

Залежності (`@testing-library/react`, `@testing-library/dom`, `@testing-library/user-event`,
`jsdom`) — у корені монорепо, одним `npm i -D`. Файл називається `*.dom.test.*`, щоб його видно
було в списку без читання.

**Правило: тест має зуби.** Тест, який проходить і з відтвореною помилкою, не вартий написання —
перевіряй мутацією (відтвори баг у коді й переконайся, що тест червоніє).

## Уся джоба однією командою

**Правило: перед пушем — `npm run verify`, а не вибіркові гейти.** Причина одна: найчастіша
причина червоного прогону — новий файл без тесту, а його ловить `check:coverage` після повного
прогону з покриттям, тобто `npm test` тут не заміна; у джобі `checks` цей гейт стоїть перед
збірками, щоб забутий тест червонів раніше за бюджет бандла. Стереже сам власник: червоний
прогін — це видимий слід, а «локально все зелене» — обіцянка.

`npm run verify` проходить кроки `checks` у тому ж порядку й зупиняється на першому червоному,
називаючи команду для повтору.

Те, що все ж проскочило, розбирає `ci-triage` — не людина й не пам'ять: клас падіння,
причина, лікування й одна нитка в issues (див. `CI_TRIAGE.md`). Перед стартом він звіряє свій список із `.github/workflows/deploy.yml`
і падає на розбіжності: крок, доданий у CI й забутий локально, інакше давав би зелене «локально все
добре» при червоному деплої — саме так і розходились локальний прогін і прод. `--only=check` жене
лише гейти, `--no-audit` — без `npm audit` (потрібен інтернет).

## Деплой — це доказ, а не припущення

Локальний `verify` не каже нічого про те, що живе на воркері: пуш іде через серверний
`cloud_git`, де локальні git-хуки не виконуються взагалі — тому хук тут був би декорацією.
Єдина ознака виконаного завдання — `npm run check:deploy`: він знаходить run workflow
**`Deploy`** саме для поточного SHA (а не «перший зелений run цього коміту» — так `CI triage`
уже видавав себе за деплой), вимагає успіху кожного job (`checks`, `deploy-bot`, `deploy-api`,
`deploy-web-admin`, `deploy-web`) і торкає живий воркер: `/health` → 200, закритий адмін-шлях
→ 401. Код виходу 0 — єдине право сказати «готово»; червоне — це не «задеплоїлось, але…».

## Як запускати

```bash
npm run verify          # уся джоба checks: гейти, обидві збірки, тести, покриття
npm run check:quality   # планка (той самий крок у CI)
npm run check:css       # «клас без правила»
npm run check:docs      # бюджет документів, мертві посилання, шляхи й згадки з коду, покажчик, свіжість API.md
npm run check:comments  # коментар довший за документний абзац і мертвий шлях у коментарі
npm run check:db        # схема D1 по реєстру
npm run build --workspace web-platform-dev
npm run build --workspace web-admin-dev
npm run check:bundle    # вага бандла оболонок (після обох build)
npm run check:deploy    # доказ деплою: run Deploy для HEAD + живий воркер (після пушу)
npm run audit:bricks    # обхід усіх поверхонь у браузері: екран, кирпичики, теми, ширина
npm run test:coverage   # прогін із покриттям (окремо, щоб npm test лишався швидким)
npm run check:coverage  # підлога покриття падає, якщо менша
npm run doc:api         # перегенерувати docs/API.md (не гейт, а лікування)
npm run clean:tmp       # прибрати кеш vite-node з /tmp (не гейт: диск, а не код)
```

Усі кроки стоять у джобі `checks` перед `npm test`: червоний гейт блокує деплой усіх чотирьох
воркерів так само, як червоний тест.

## Кирпичики перевіряються на екрані

`check:css` бачить лише те, що клас має правило: він не бачить, що сторінка вилазить за екран,
що всередині картки з’явився власний скролер або що підпис обрізався без «…». Це видно тільки
в браузері, тому `npm run audit:bricks` відкриває **кожну** поверхню і міряє геометрію:
документ не ширший за вікно, жоден елемент не виходить за екран (крім вмісту скролерів-кирпичиків),
липкий хром стоїть у межах екрана, горизонтально гортає лише кирпичик, текст не обрізаний
без скролера й без «…», інтерактивна ціль — не менша за 24px. Перелік сторінок **не
рукописний**: платформа бере рядки з найсвіжішого дампа бази сценаріїв (`backups/dev-scenarios-*.json`),
адмінка й екрани платформи — з `app/router.tsx`, тож нова сторінка потрапляє в обхід сама.
Обидві теми, 360px і 1280px. Крок не стоїть у `checks`: йому потрібні браузер і підняті
сервери оболонок, тому він — ручний доказ перед пушем, а не частина CI.
