## 🧭 Концепція: «Кришталевий код»
«Кришталевий код» — це стан системи, де:
1. **Кожен модуль виконує одну роль (SRP)**, не має прихованих побічних ефектів і передбачуваний для тестування.
2. **Типізація є вичерпною та строгою**: нуль неконтрольованих `any`, контракти між клієнтом і бекендом зафіксовані схемами.
3. **Архітектура фрактальна**: однакові патерни повторюються на всіх рівнях (вхід → валідація → сервіс/стан → вивід).
4. **Автоматизований захист**: тести й лінтери гарантують відсутність регресій при будь-яких змінах як людиною, так і AI-агентами.

## 📋 Топ-9 системних завдань для рефакторингу

### 1. 🛡️ Впровадження автоматизованих тестів (Scorecard: 0/9 ➔ 5/9) (✅ Виконано)
* **Проблема:** У репозиторії наразі відсутні тести (`*.test.ts`, `*.spec.ts`) та тестовий фреймворк. Будь-який рефакторинг несе ризик непомітної регресії.
* **Рішення:**
  * Додати **Vitest** у кореневий `package.json` або у відповідні воркери (`api-dev`, `bot-dev`, `packages/shared`).
  * Покрити unit-тестами чисті функції:
    * `formatSqliteDatetime()`
    * Розрахунки та валідації дат у `packages/shared` / `api-dev`
    * Парсинг та валідацію схем `Family Box` та сценаріїв бота
    * Утиліти `screen.ts` та маппінг Telegram-повідомлень
* **Очікуваний результат:** Створення базової сітки безпеки (15-20 тестів), підняття оцінки в Scorecard з 0 до 6+.

---

### 2. 📦 Очищення та стандартизація Lock-файлів у Monorepo (✅ Виконано)
* **Проблема:**
  * У корені є `package-lock.json`.
  * Окремо зберігаються локальні `package-lock.json` у `web-admin-dev/`, `api-dev/`, `bot-dev/`.
  * У `web-platform-dev/` лежить `bun.lock`.
* **Рішення:**
  * Видалити всі підпапкові lock-файли (`bun.lock`, локальні `package-lock.json`).
  * Використовувати **єдиний кореневий `package-lock.json`** на базі npm workspaces.
  * Додати блокування в `.gitignore`: `*/package-lock.json` та `*.lock` (окрім кореневого).
* **Очікуваний результат:** Детерміновані збірки в CI/CD без конфліктів версій і дублювання кешу залежностей.

---

### 3. 🎨 Уніфікація стилів: перехід з 4500+ рядків ручного CSS на Tailwind 4
* **Проблема:**
  * `web-admin-dev/src/index.css` містить **3 196 рядків**.
  * `web-platform-dev/src/index.css` містить **1 454 рядки**.
  * Велика кількість жорстко закодованих селекторів конкурує з утилітами Tailwind 4 та дизайн-токенами з `packages/shared/src/styles/`.
* **Рішення:**
  * Провести аудит класів `index.css`: перенести змінні тем (Apple / Material) до єдиної дизайн-системи.
  * Замінити кастомні класи кнопок, карток і полів введення на utility-класи Tailwind 4 або перевірені спільні компоненти.
  * Скоротити розмір `index.css` у кожному веб-додатку до < 150-200 рядків.
* **Очікуваний результат:** Швидший рендеринг, відсутність специфічності CSS-конфліктів, легка зміна тем оформлення.

---

### 4. 🧩 Сервісний шар та декомпозиція `users.controller.ts` в `api-dev`
* **Проблема:** `api-dev/src/controllers/users.controller.ts` (531 рядок, 16.3 KB) поєднує HTTP-роутинг, валідацію вхідних параметрів, прямі SQL-запити до D1, бізнес-логіку авто-міграцій та парсинг JSON.
* **Рішення:**
  * Створити `api-dev/src/services/users.service.ts`.
  * Винести операції з базою D1 та обробку бізнес-полів (`family_box`, `topics`, `my_dates`) у сервіс.
  * Залишити в контролері виключно транспортну роль: валідація `req` → виклик `userService` → повернення `res.json()`.
* **Очікуваний результат:** Ізольоване тестування бізнес-логіки без мокання HTTP-запитів, контролер скорочується до < 150 рядків.

---

### 5. 🎯 Ліквідація 100+ `any` та повна строгість типів (Задача P2-1)
* **Проблема:** Наявність ~101 використання `any` заважає статичному аналізатору TypeScript відловлювати помилки на етапі компіляції.
* **Рішення:**
  * Задекларувати суворі типи/інтерфейси для:
    * Структури `FamilyBox` та його підрозділів (cart, custom_dates, games).
    * Telegram Bot API payload & callback data.
    * Cloudinary upload/transform responses.
  * Увімкнути правило `@typescript-eslint/no-explicit-any: "warn"` (і згодом `"error"`).
  * Використовувати `unknown` з user-defined type guards замість `any` під час десеріалізації JSON.
* **Очікуваний результат:** Відсутність runtime-помилок `Cannot read properties of undefined`, бездоганний автокомпліт у коді.

---

### 6. 📐 Єдина валідація контрактів (Contract-first через Zod або TypeBox)
* **Проблема:** Валідація складних структур (сценарії, дати, користувацькі конфіги) здійснюється вручну або фрагментарно, створюючи розрив між тим, що очікує бот, що повертає API і що відображає TWA.
* **Рішення:**
  * Впровадити єдині схеми валідації в `packages/shared/src/schemas/`.
  * Валідувати вхідні дані на рівні роутера API (`safeParse`) та генерувати типи прямо зі схем (`z.infer<typeof ...>`).
* **Очікуваний результат:** Неможливість зберегти в базу D1 некоректний JSON, автоматичні зрозумілі помилки 400 Bad Request із зазначенням некоректного поля.

---

### 7. 🧱 Розбиття UI-монолітів на Feature-модулі
* **Проблема:** Компоненти-моноліти:
  * `web-admin-dev/src/features/page-builder/PageBuilderInline.tsx` (573 рядки)
  * `web-admin-dev/src/pages/scenarios-v2/ScenariosV2Table.tsx` (534 рядки)
  * `web-platform-dev/src/pages/mydate/MyDatesPage.tsx` (414 рядків)
  * `web-admin-dev/src/pages/scenarios/ScenarioCardModal.tsx` (331 рядок)
* **Рішення:**
  * Відокремити логіку стану від представлення за допомогою кастомних хуків:
    * `usePageBuilderState()`
    * `useScenariosFilter()`
    * `useMyDates()`
  * Розбити візуальні частини на окремі чисті підкомпоненти (Header, TableRow, ActionsModal, Preview).
* **Очікуваний результат:** Зниження складності файлів до < 150-200 рядків, відсутність паразитичних ререндерів, легкість читання коду.

---

### 8. 🔭 Спостережуваність та перехоплення помилок (Observability)
* **Проблема:** Бот логує через чергу, але в API логування локальне, а на фронтенді помилки користувача залишаються лише в консолі браузера.
* **Рішення:**
  * Впровадити React `ErrorBoundary` у `web-platform-dev` та `web-admin-dev` зі зрозумілим fallback UI.
  * Налаштувати централізоване логування критичних помилок (через Telegram-топік сповіщень або Sentry).
  * Додати кореляційний `x-request-id` між TWA → API → D1.
* **Очікуваний результат:** Миттєва обізнаність про будь-які збої в боті чи адмінці без ручного перегляду Cloudflare Logs.

---

### 9. 🚀 CI/CD ворота якості (Quality Gates) та документація
* **Проблема:** У CI зараз запускається деплой і аудит, але відсутній строгий контроль якості перед мерджем у `main`.
* **Рішення:**
  * Додати обов'язковий workflow у GitHub Actions:
    * `npm run lint`
    * `npm run typecheck`
    * `npm run test`
  * Додати файли `CONTRIBUTING.md` та `CHANGELOG.md` для регламенту внесення правок як людьми, так і AI-агентами.
* **Очікуваний результат:** 100% гарантія того, що жоден коміт не зламає типізацію чи існуючі тести перед деплоєм у Cloudflare.
