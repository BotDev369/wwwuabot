# wwwuabot — Система оцінки проєкту + чесна оцінка станом на 26.08.2026

Мета документа: дати єдину, повторювану шкалу, за якою можна оцінити проєкт
сьогодні, а потім — через місяць, через рік — і побачити прогрес. Шкала
розрахована на аудиторію, яку ви назвали: IT-спеціалісти, AI-агенти,
партнери, інвестори, регулятори. Тому серед критеріїв є не лише "чистота
коду", а й речі, які цікавлять саме цих людей: безпека даних, прозорість
ліцензії, готовність до зовнішнього рев'ю.

---

## Як працює система

- 10 критеріїв, кожен оцінюється від **0 до 9**.
- Для кожного критерію є опис, що означає 0, 3, 6 і 9 — щоб оцінка не була
  "на око", а щоб будь-хто (людина чи AI-агент) міг повторно оцінити проєкт
  за тими самими орієнтирами й отримати порівнювані цифри.
- Підсумок — простий середній бал (без штучних вагових коефіцієнтів,
  щоб система була прозорою й легко пояснюваною).
- Це не "екзамен на відмінно" — це знімок стану проєкту на конкретну дату,
  який має сенс лише в порівнянні з наступним знімком.

## Критерії оцінки

### 1. Архітектура та структура коду
Наскільки логічно організований код: чи легко знайти потрібну логіку,
чи немає "богоподібних" файлів на тисячі рядків, чи однакова структура
використана в подібних частинах проєкту.

| Бал | Опис |
|---|---|
| 0 | Весь код в одному-двох файлах, немає поділу на модулі. |
| 3 | Є спроба структури, але непослідовна: частина проєкту організована, частина — суцільний файл. |
| 6 | Більшість проєкту має чітку, повторювану структуру; є окремі слабкі місця. |
| 9 | Кожна частина проєкту дотримується однієї продуманої архітектури, легко передбачити, де шукати код. |

### 2. Консистентність і стандарти коду
Чи є автоматичний лінтер/форматер, чи стиль коду (відступи, лапки,
іменування) однаковий по всьому репозиторію незалежно від того, хто
(людина чи яка саме AI-модель) писав конкретний файл.

| Бал | Опис |
|---|---|
| 0 | Немає лінтера/форматера, стиль коду відрізняється від файлу до файлу. |
| 3 | Лінтер є в одній частині проєкту, в інших — відсутній. |
| 6 | Лінтер+форматер підключені всюди, але не в CI (можна закомітити код, що їх не пройшов). |
| 9 | Лінтер+форматер підключені всюди і **блокують** коміт/деплой при порушенні. |

### 3. Безпека
Секрети не в коді, середовища prod/dev розділені, є перевірка вразливостей
у залежностях, авторизація захищає адмінські дії.

| Бал | Опис |
|---|---|
| 0 | Секрети в коді, prod/dev не розділені, немає перевірки залежностей. |
| 3 | Секрети винесені, але є структурні ризики (напр. змішання prod/dev) або немає перевірки залежностей. |
| 6 | Секрети й середовища в порядку, є базова перевірка залежностей (напр. Dependabot). |
| 9 | Все з рівня 6 + регулярний аудит доступів, авторизації, і план реакції на витік. |

### 4. CI/CD і розгортання
Чи автоматизований деплой, чи деплоїться лише те, що змінилось, чи є
перевірки (лінт/тести) перед деплоєм, чи є контрольований rollback.

| Бал | Опис |
|---|---|
| 0 | Деплой вручну, без автоматизації. |
| 3 | Є автодеплой, але без фільтрації змін і без перевірок перед деплоєм. |
| 6 | Автодеплой з фільтрацією змінених частин, є лінт/білд-перевірка перед деплоєм. |
| 9 | Все з рівня 6 + окремі environments з підтвердженням для прод, легкий rollback. |

### 5. Тестування
Наявність автоматичних тестів (unit/integration), що ловлять регресії
до того, як їх побачить користувач.

| Бал | Опис |
|---|---|
| 0 | Тестів немає взагалі. |
| 3 | Є поодинокі тести критичних функцій, без системи. |
| 6 | Основна бізнес-логіка покрита тестами, тести запускаються в CI. |
| 9 | Широке покриття (unit+integration), тести — обов'язкова умова мержу. |

### 6. Документація для людей
README, інструкції для запуску локально, опис змінних середовища,
опис бізнес-логіки (напр. що таке "Scenario", "Family Box").

| Бал | Опис |
|---|---|
| 0 | Документації немає або вона застаріла. |
| 3 | Є README, але без інструкцій запуску/налаштування. |
| 6 | README + інструкції для розробника (як запустити, які env-змінні потрібні). |
| 9 | Все з рівня 6 + документація по кожному сервісу окремо, CHANGELOG, приклади використання API. |

### 7. Дружність до AI-агентів
Чи легко AI-агенту (не лише мені — будь-якому) зрозуміти проєкт без
довгих розкопок: передбачувані назви файлів/функцій, явний опис
конвенцій (напр. `AGENTS.md`/`CLAUDE.md`), відсутність "магії" без
пояснень у коді.

| Бал | Опис |
|---|---|
| 0 | Немає жодних орієнтирів, кожен AI-агент змушений вгадувати структуру заново. |
| 3 | Структура коду частково передбачувана, але немає явного опису конвенцій. |
| 6 | Є передбачувана структура + базовий опис конвенцій в README. |
| 9 | Є окремий файл-інструкція для AI-агентів з описом конвенцій, бізнес-термінів, "не роби так". |

### 8. Спостережуваність (Observability)
Логування, обробка помилок, можливість зрозуміти "що пішло не так"
без доступу до живого сервера в момент інциденту.

| Бал | Опис |
|---|---|
| 0 | Немає логування, помилки не фіксуються ніде. |
| 3 | Є `console.log` подекуди, немає єдиного підходу. |
| 6 | Є єдиний логер хоча б в одній ключовій частині проєкту. |
| 9 | Структуроване логування й обробка помилок у всіх сервісах + зовнішній моніторинг/алерти. |

### 9. Приватність даних і відповідність вимогам
Наявність ліцензії, політики приватності (особливо якщо проєкт збирає
особисті дані користувачів — дати народження, імена), прозорість щодо
того, як дані використовуються.

| Бал | Опис |
|---|---|
| 0 | Немає ні ліцензії, ні політики приватності, хоча збираються особисті дані. |
| 3 | Є згадка ліцензії/власності, але без формального файлу чи політики приватності. |
| 6 | Є файл LICENSE і базова політика приватності/умови використання. |
| 9 | Все з рівня 6 + чіткий процес видалення даних користувача на запит, відповідність вимогам на кшталт GDPR. |

### 10. Готовність для зовнішніх стейкхолдерів
Як проєкт виглядає для людини "ззовні" за перші 5 хвилин: інвестора,
партнера, потенційного контриб'ютора. Бренд, ясність, professionalism.

| Бал | Опис |
|---|---|
| 0 | Репозиторій виглядає як особистий чернетковий проєкт. |
| 3 | Є охайний README, але немає інших сигналів "зрілості" (badges, roadmap, CONTRIBUTING). |
| 6 | README + badges (build status, license) + CONTRIBUTING + видима активність (commits, issues). |
| 9 | Все з рівня 6 + публічний roadmap, changelog, чіткий процес для контриб'юторів і партнерів. |

## Що це число означає (і чого не означає)

Це нормальний, очікуваний результат для проєкту на етапі активної розробки,
де основний фокус був на тому, щоб "воно працювало", а не на процесах
навколо коду. Найсильніші сторони — саме там, де хтось (людина чи AI)
свідомо думав наперед: архітектура `bot/`, зміст README, логування через
чергу. Найслабші — там, де процес просто ще не був запущений: тести,
лінтер, приватність/ліцензія, CI з перевірками.

Важливий нюанс: два найнижчі бали (**Тестування — 0** і **Приватність/
відповідність — 2**) — це не "технічний борг у коді", а **відсутність
процесу як такого**. Це водночас і погана новина (найбільший розрив),
і хороша (їх найлегше підняти на кілька балів швидко, бо починаємо з нуля,
а не розплутуємо щось складне).

## Топ-3 напрямки з найбільшим ефектом на загальний бал

1. **Тестування (зараз 0)** — не потрібно 100% покриття одразу; навіть
   тести на 5-10 найкритичніших функцій (розрахунок гороскопу, валідація
   дат) підіймуть бал з 0 до 3-4 і, що важливіше, дадуть реальний захист
   від регресій під час подальшого рефакторингу.
2. **Консистентність (зараз 2)** — додати ESLint+Prettier на всі 4 сервіси
   (P0-2) та налаштувати CI з лінт-гейтом (CI-1).
3. **CI/CD (зараз 3)** — перейти на GitHub Actions з фільтром змінених
   папок та лінт/білд-гейтом перед деплоєм.
