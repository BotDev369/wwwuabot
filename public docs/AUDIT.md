# Аудит проєкту wwwuabot — детальний розбір і план стандартизації

**Дата аудиту:** 25.08.2026
**Що перевірено:** структура 4 Cloudflare Workers (`bot/`, `api/`, `web/`, `web-admin/`), конфіги (`wrangler.toml`, `package.json`), ключові файли роутингу/логіки, стилі, наскрізні патерни (пошук `any`, `console.log`, дублювання коду).

**Загальний висновок:** архітектура `bot/` (core/modules/shared/repositories) — продумана і не потребує переписування з нуля. Основні проблеми — не "каша всередині файлів", а **відсутність спільних правил між частинами проєкту**: немає лінтера на 3 з 4 сервісів, немає спільного місця для дублюючого коду, і один сервіс (`api/`) писався в іншому стилі, ніж решта.

### 🔴 P0-1. `web-admin` не розділяє production і development бази даних

```markdown
## Проблема
Файл `web-admin/wrangler.toml` — єдиний з 4 конфігів проєкту, який НЕ має
секцій `[env.production]` / `[env.dev]`. Замість цього `d1_databases`
прописана на верхньому рівні і напряму вказує на **dev-базу**
(`wwwuabot-db-dev`, id `9fc03f61-...`).

Для порівняння: `bot/wrangler.toml` і `api/wrangler.toml` чітко розділяють
`env.production` (база `wwwuabot-db-prod`) і `env.dev` (база `wwwuabot-db-dev`).

## Чому це небезпечно
Якщо адмінку задеплоїти командою без явного `--env production`
(а такої команди в `web-admin/package.json` наразі й немає — там лише
`wrangler dev --remote`), вона піде працювати з dev-базою навіть у "проді".
Через адмінку редагують сценарії бота — тобто ризик: адміністратор думає,
що редагує прод-контент, а насправді пише в тестову базу (або навпаки,
якщо колись з'явиться прод-конфіг і хтось переплутає середовища).

## Що зробити
1. Додати в `web-admin/wrangler.toml` `[env.production]` з окремим
   `database_id` для `wwwuabot-db-prod` (той самий id, що в `bot/wrangler.toml`
   і `api/wrangler.toml`: `6e690692-7671-4598-826c-c2db591399a2`).
2. Залишити верхньорівневу секцію `[[d1_databases]]` тільки для локальної
   розробки (`wrangler dev` без `--env`), і додати явний коментар у файлі,
   що це dev-only.
3. Додати в `package.json` скрипти `deploy:dev` і `deploy:prod` за зразком
   `bot/package.json`, щоб виключити людську помилку "забув --env".

## Пріоритет
🔴 P0 — це єдина розбіжність, яка може призвести до реальної плутанини
даних між середовищами. Виправляється швидко (5-10 хв), ризик високий.
```

### 🔴 P0-2. Немає лінтера й форматера на 3 з 4 сервісів

```markdown
## Проблема
З чотирьох Workers лінтер (`eslint.config.js`) є тільки в `web-admin/`.
У `bot/`, `api/`, `web/` немає ні ESLint, ні Prettier, ні жодного
`.editorconfig`. Це підтверджується і на практиці: у файлі
`bot/src/core/errors.ts` — відступи по 4 пробіли, а в сусідньому
`bot/src/core/router/bot-router.ts` — по 2 пробіли. Немає єдиного стилю
лапок (одинарні/подвійні змішані).

## Чому це корінь проблеми "різні AI — різний стиль"
Коли над кодом по черзі працюють різні моделі/агенти, єдине, що реально
утримує стиль в одних рамках — автоматичний лінтер + форматер, які
запускаються перед комітом (pre-commit hook) або в CI. Без них кожен новий
агент (у т.ч. я) пише "по-своєму", і розбіжності накопичуються назавжди.

## Що зробити
1. Додати єдиний `eslint.config.js` + `prettier.config.js` в корінь
   репозиторію (Flat Config, сумісний з ESLint 9, як уже є в `web-admin`).
2. У кожному з 4 проєктів (`bot`, `api`, `web`, `web-admin`) підключити
   ці кореневі конфіги через `extends`/`import`, з мінімальними
   локальними відхиленнями (напр. React-hooks правила лише для `web`/`web-admin`).
3. Зафіксувати єдиний стиль: 2 пробіли, подвійні лапки, крапка з комою —
   так, як переважає в `bot/` зараз (це найбільша і найпослідовніша частина).
4. Додати `npm run lint` і `npm run format` у кожен `package.json`,
   і (за бажанням) git hook через `husky` + `lint-staged`, щоб форматування
   застосовувалось автоматично при коміті.
5. Одноразово прогнати `prettier --write` по всьому репо, закомітити
   окремим комітом "chore: normalize formatting" — щоб цей комміт не
   змішувався зі змістовними правками (легше рев'ювити історію).

## Пріоритет
🔴 P0 — не тому що щось "зламано", а тому що без цього кроку всі наступні
покращення (P1-P3) будуть знову розмиватись з кожним новим агентом,
який торкається коду. Це найдешевший фікс з найбільшим довгостроковим ефектом.
```

### 🟠 P1-1. `api/src/index.ts` — весь бекенд в одному файлі на 612 рядків без роутера

```markdown
## Проблема
`api/src/index.ts` містить одразу: health-check, розрахунки західної
астрології (гороскопи), CRUD для "моїх дат" користувача, порівняння систем,
роботу з D1 і KV — все в одному `fetch()` з ланцюжком
`if (url.pathname === ...) { ... }`. Немає жодного `package.json` чи
`tsconfig.json` у цій директорії — єдиний Worker з чотирьох без них.

Для порівняння, `bot/src/` уже має правильну структуру:
`api/router.ts` + `api/controllers/*.controller.ts`, кожен контролер —
окремий файл з чіткою відповідальністю.

## Чому це проблема
- Будь-яка зміна в одній фічі (напр. гороскопах) вимагає скролити
  600-рядковий файл і ризикує зачепити сусідню логіку (CRUD дат).
- Без `package.json` неможливо додати залежності, лінтер чи типи окремо
  для цього Worker — він "живе на чужому" TypeScript-конфізі.
- Немає жодного тесту чи типізованого контракту між ендпоінтами.

## Що зробити
1. Додати `api/package.json` і `api/tsconfig.json` (взяти за шаблон
   `bot/tsconfig.json`, спростивши під один файл-воркер).
2. Розбити `index.ts` за прикладом `bot/src/api/router.ts`:
   ```
   api/src/
     router.ts                    # тонкий роутер (switch по pathname+method)
     controllers/
       health.controller.ts
       astrology.controller.ts    # розрахунки гороскопів + SIGN_META/SIGN_CUTOFFS
       my-dates.controller.ts     # CRUD дат (GET/POST/PUT/DELETE)
       scenario.controller.ts     # resolveScenario, BASE_CONFIG
       compare.controller.ts      # /api/compare матриця
     services/
       analysis.service.ts        # getAnalysis/saveAnalysis (KV+D1 кеш)
     shared/
       validators.ts              # спільні валідатори (дивись P1-3)
   ```
3. `export default { fetch }` залишити мінімальним — тільки виклик роутера.

## Пріоритет
🟠 P1 — не блокує роботу зараз, але кожна наступна зміна в `api/`
буде дорожчою й ризикованішою, поки файл не розбитий.
```

### 🟠 P1-2. Дубльована логіка авто-міграції колонок D1 — `api` винайшло свій велосипед

```markdown
## Проблема
У `bot/src/core/database/auto-migrate.ts` вже є перевикористовувана,
акуратно написана функція `withAutoMigrate()`: вона перехоплює помилку
"no such column", сама визначає SQLite-тип за прикладом значення і додає
колонку через `ALTER TABLE`.

У `api/src/index.ts` (рядки ~118-125) написана **інша, спрощена версія**
тієї самої ідеї — `ensureMyDatesColumn()`, яка робить `PRAGMA table_info`
і вручну перевіряє наявність однієї конкретної колонки `my_dates`.
Це та сама задача, вирішена двічі, по-різному, різними інструментами
(бот — через try/catch навколо запиту, api — через окрему PRAGMA-перевірку
перед кожним запитом).

## Чому це проблема
- Якщо завтра з'явиться потреба в новій колонці (напр. `preferences`),
  хтось повторить це втретє — вже по-своєму.
- Дві реалізації можуть розійтись у поведінці (напр. типи колонок,
  обробка помилок), і дебажити доведеться в двох місцях.
- `PRAGMA table_info` в `api` виконується **на кожен запит** до
  `/api/my-dates`, навіть коли колонка вже існує — зайве навантаження на D1.

## Що зробити
Оскільки `bot/` і `api/` — окремі Workers без спільного npm-пакета,
є два варіанти (обрати один):

**Варіант A (швидший):** перенести `withAutoMigrate` і `inferSqliteType`
з `bot/src/core/database/auto-migrate.ts` в `api/src/shared/`
(буквальна копія файлу, без імпорту між проєктами) і використати в `api`
замість `ensureMyDatesColumn`.

**Варіант B (правильніший, більше роботи):** винести спільний код
(`auto-migrate`, форматування дат з P1-3, типи) в окремий npm-пакет
`packages/shared/` в корені монорепо і підключити його в `bot` і `api`
через `npm workspaces` (див. P2-3).

## Пріоритет
🟠 P1 — конкретний працюючий дублікат логіки з різницею в поведінці.
Варіант A можна зробити за 15 хвилин просто зараз.
```

### 🟠 P1-4. Список типів дат (`VALID_TYPES`) продубльований тричі в одному файлі

```markdown
## Проблема
У `api/src/index.ts` масив `const VALID_TYPES = ["person", "event", "other"]`
оголошений **окремо тричі**: у блоці міграції старих записів (~рядок 476),
в обробнику `POST` (~рядок 528, як `VALID_TYPES`) і в обробнику `PUT`
(~рядок 561, під іншим ім'ям `VALID_TYPES_PUT`, хоча значення те саме).

## Чому це проблема
Якщо колись додасться новий тип дати (напр. `"anniversary"`), потрібно
пам'ятати про всі три місця. Друга назва змінної (`VALID_TYPES_PUT`)
натякає, що хтось (людина чи AI) уже боявся зачепити існуючий код і просто
скопіював константу під новим ім'ям, замість повторного використання.

## Що зробити
1. Винести `const VALID_TYPES = ["person", "event", "other"] as const;`
   один раз на рівень модуля (на початок файлу або в окремий
   `api/src/shared/constants.ts` після розбиття з P1-1).
2. Прибрати дублікат `VALID_TYPES_PUT`, використати той самий масив.
3. За бажанням — типізувати: `type DateType = typeof VALID_TYPES[number];`
   замість `type: string` в інтерфейсах.

## Пріоритет
🟠 P1 — швидко, безпечно, прибирає конкретне джерело неузгодженості.
```

### 🟡 P2-1. Надмірне використання `any` — особливо в `api/`

```markdown
## Проблема
У всьому репозиторії 101 використання `any` (`: any`, `<any>`, `as any`).
Найбільша концентрація — `api/src/index.ts` (23 випадки), далі
`bot/src/shared/utils/screen.ts` (5), `bot/src/modules/games/tictactoe/render.ts` (5),
`web-admin/src/features/editor/store.ts` (4).

## Чому це проблема
TypeScript підключений у всіх 4 проєктах, але там, де найбільше `any`,
він фактично не захищає від помилок — на етапі компіляції не будуть
пійматись, наприклад, помилки в назвах полів об'єкта `analysis[sys.id]`
чи `result.parameters`.

## Що зробити
Не потрібно виправляти всі 101 одразу — це великий і не терміновий обсяг
роботи. Пропоную поетапно:
1. Почати з `api/src/index.ts` під час розбиття з P1-1 — заодно описати
   реальні типи для `Env`, `Analysis`, `MyDate`, `ScenarioConfig`.
```

### 🟠 CI-1. Перехід з нативної Cloudflare Git-інтеграції на GitHub Actions

```markdown
## Поточний стан
У репозиторії немає `.github/workflows/` — деплой іде через нативну
Git-інтеграцію Cloudflare Workers Builds: кожен з 4 Workers-проєктів
(`bot`, `api`, `web`, `web-admin`) підключений напряму в дашборді
Cloudflare до цього GitHub-репо. Наслідок: **будь-який пуш, навіть у
файл однієї з 4 папок, тригерить білд і деплой усіх чотирьох Workers**,
хоча змінився лише один.

## Чому вирішили перейти на GitHub Actions (а не просто "Build Watch Paths")
Розглядали 3 варіанти:
1. Залишити нативну Cloudflare-інтеграцію, додати "Build Watch Paths" в
   дашборді (найшвидше, але без gate на лінт/тести перед деплоєм).
2. **Перейти на GitHub Actions + `wrangler deploy`, з фільтром змінених
   папок** — обрано цей варіант.
3. GitHub Actions + окремий крок AI-рев'ю на PR перед деплоєм —
   заплановано як можливий наступний крок ПІСЛЯ того, як варіант 2
   попрацює стабільно кілька тижнів.

Причина вибору варіанту 2 замість 1: у документі вище вже заплановано
ESLint+Prettier (P0-2). Нативна Cloudflare-інтеграція не вміє зупинити
деплой, якщо лінтер знайшов помилку — вона просто білдить і деплоїть.
GitHub Actions дозволяє вставити крок "lint + build" **перед**
`wrangler deploy`, і якщо він падає — деплою просто не буде. Це і є
той "стандарт", який просив власник проєкту: щоб зламаний код
не міг випадково потрапити в прод, хто б його не написав — людина чи AI.

## Квоти (перевірено окремо, репозиторій публічний)
GitHub Actions на публічних репозиторіях зі стандартними
GitHub-hosted runners (`ubuntu-latest`) — **безкоштовний і без
місячного ліміту хвилин**. Ліміт 2000 хв/міс стосується лише
приватних репозиторіїв на Free-плані GitHub. Тобто для цього проєкту
квота не є обмеженням і не потребує моніторингу як бюджет — просто
уникати "larger runners" і self-hosted runners (вони платні навіть
у публічних репо, і в цьому проєкті не потрібні: `wrangler deploy` —
легка CLI-команда, звичайного `ubuntu-latest` більш ніж достатньо).

## Що зробити технічно
1. **Підготувати секрет:** створити Cloudflare API Token (Workers Scripts:
   Edit) і додати його в GitHub repo → `Settings → Secrets and variables →
   Actions` під назвою `CLOUDFLARE_API_TOKEN`. Також додати
   `CLOUDFLARE_ACCOUNT_ID` як звичайну (не секретну) variable.
2. **Створити `.github/workflows/deploy.yml`** в корені репо зі структурою:
   - тригер: `on: push: branches: [main]`
   - job з `dorny/paths-filter@v3` — визначає, які з 4 папок (`bot/**`,
     `api/**`, `web/**`, `web-admin/**`) змінились у поточному пуші
   - для кожного воркера — окремий job з `if: needs.changes.outputs.<worker> == 'true'`,
     кроки: checkout → `npm ci` у відповідній папці → (коли з'явиться
     лінтер з P0-2) `npm run lint` → `npm run build` (якщо є) →
     `wrangler deploy --env production` через `cloudflare/wrangler-action@v3`
   - окремо — job(и) для деплою в `env: dev` при пуші в гілку `develop`
     (за бажанням, якщо є окрема dev-гілка)
3. **Вимкнути нативну Git-інтеграцію** в дашборді Cloudflare для всіх 4
   Workers-проєктів (`Settings → Build → Git` → Disconnect), щоб не було
   подвійного деплою (і від Cloudflare, і від Actions одночасно).
4. **Перевірити на dev** перед вимкненням нативної інтеграції: зробити
   тестовий пуш у гілку, переконатись, що workflow задеплоїв лише
   очікуваний воркер, і лише після цього відключати Cloudflare Git-інтеграцію.

## Пріоритет
🟠 P1 (за тією ж шкалою, що й код-пункти вище) — не терміново в сенсі
"щось зараз ламається", але напряму впливає на безпеку деплоїв (у
зв'язці з P0-1 і P0-2 — лінт-гейт і розділення prod/dev стають реально
ефективними лише коли є CI, що їх перевіряє). Робити одразу після P0-1/P0-2.
```
