# web-platform-dev

Cloudflare Worker: Telegram Mini App для wwwuabot (React 19 + Vite 8 + Tailwind 4).

## Налаштування

- **Service binding:** `API` → `api-dev` (увесь трафік `/api/*` іде туди)
- **D1:** немає — прямувати до бази цей воркер не має права
- **Секрети:** не потрібні (авторизація — підписаний Telegram `initData`)
- **Середовище:** `ENVIRONMENT = "dev"` — задеплоєний лише дев-воркер, прода немає

## Мобільний — пріоритет №1

Це єдина точка взаємодії користувачів, і майже завжди — телефон. Тому в цьому
застосунку перевіряють **спочатку 360px**, а десктоп — потім. Обовʼязково:

Правила (резинова верстка, `100dvh` + `var(--safe-*)`, `viewport-fit=cover`, тап-таргети ≥ 44px,
афорданси без `:hover`, **ніяких** `alert` / `confirm` / `prompt` — тільки `useDialog()`) —
`AGENTS.md` §3 і §4.

## Роути

Один маршрут — **контент**; решта — екрани, які не є рядком `scenarios`. Повний
перелік і власник адрес — `src/app/router.tsx` і `src/app/routes.ts`.

| Шлях | Що це |
|---|---|
| `*` | catch-all: сторінка за її адресою (`slug`) — рендерить `pages/ScenarioPage.tsx` |
| `/account`, `/orders` | дані людини й робота магазинів, які вона веде |
| `/favorites`, `/services` | обрані сторінки та список сервісів |
| `/ads`, `/games`, `/games/:key`, `/users` | відкритий вміст: дошка оголошень, ігри, люди |
| `/notes`, `/contacts`, `/messages`, `/assessments/:key?` | власні дані людини |
| `/pages`, `/pages/new`, `/pages/:id` (+ `products`, `orders`, `edit`) | сторінка з шаблону та її робота |

Адреса контенту сегментами — це адреса рядка `scenarios`, а хвіст адреси — його
параметри. Другої навігації по тому самому контенту (ієрархії «сайтів» зі своїми
таблицями) не існує — інакше правило «яка сторінка для цього URL» жило б у двох місцях
одразу.

| Адреса вебу | Та сама сторінка в боті |
|---|---|
| `/` | `t.me/<bot>` (головна) |
| `/dateanalysis/19800303/today` | `t.me/<bot>?start=dateanalysis_19800303_today` |

Подання адреси будує `packages/shared/src/content/resolve.ts`
(`toWebPath` / `toBotPayload`), готове посилання для «Поділитись» —
`buildShareLinks()`. Деталі — `docs/CONTENT_MODEL.md`.

## Прев'ю в браузері: сесія Telegram і e2e

Поза Telegram `initData` порожній, і `AuthGate` навмисно не малює нічого — тому
у звичайному браузері застосунок виглядає як порожня сторінка. Щоб прев'ю
справді показувало платформу, сервер розробки підписує **справжній** `initData`
(`dev/telegram-session.ts`): той самий алгоритм, що й у Telegram, тож `api-dev`
перевіряє його своєю звичайною перевіркою — жодних винятків у ній не з'являється.
Токен читає сервер розробки, у бандл він не потрапляє (плагін стоїть із
`apply: "serve"`, у продакшн-збірці його немає); у браузер їде лише підписаний
рядок — те саме, що Telegram віддає клієнту Mini App.

| Змінна оточення | Що це |
|---|---|
| `BOT_TOKEN_DEV` | токен **дев**-бота — те саме значення, що в секреті `BOT_TOKEN` в `api-dev` |
| `PREVIEW_TELEGRAM_ID` | Telegram-id, від чиєї особи відкривається прев'ю: власник або запрошена людина. Список через кому: перший — типовий, решта — для `?as=<id>` |
| `API_DEV_URL` | адреса задеплоєного `api-dev` — туди йде `/api/*` (див. `vite.config.ts`) |

Без перших двох сервер розробки друкує в лог попередження, а прев'ю лишається
порожнім — це названа причина, а не поломка.

**Два акаунти на одній адресі.** `?as=<id>` підписує сесію від іншого id зі
списку (`/?as=6281898553`) — так один прогін перевіряє і власника, і звичайну
людину. Id поза списком не підписується зовсім, тож прев'ю не видає чужого
імені. Другому акаунту потрібен допуск: `users.inviter_id` пише бот при переході
за контактом-запрошенням, і без нього гейт відповідає відмовою — це правило
продукту, а не прев'ю.

E2E: `npm --prefix web-platform-dev run test:e2e` — Playwright (Chromium,
360×780) проти вже піднятого прев'ю, сам сервер він не піднімає. Перевіряє
сесію, гейт допуску, навігацію, мобільні мірки й помилки консолі; знімки
екранів лягають у `e2e-artifacts/`. Підпис і обгортку `Telegram.WebApp` окремо
перевіряє `npm test` (`dev/telegram-session.dom.test.ts`).
